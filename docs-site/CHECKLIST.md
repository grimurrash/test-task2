# Чек-лист проверки страницы

Что прогонять перед тем, как сказать «страница работает». Список короткий
намеренно: каждый пункт здесь появился после того, как что-то из него однажды
не поймалось.

**Команды выполняются дословно, сверху вниз.** Рабочий каталог указан перед
каждым блоком и меняется между шагами — это не придирка к оформлению: шаги
1–5 живут в `docs-site/`, а образ собирается из корня репозитория, потому что
странице нужен `openapi/openapi.yaml`.

## Чем этот чек-лист не является

Он **не механизм**. Сборка падает сама на неполном контракте — это механизм,
он сработает у всех. Всё остальное здесь, включая `tools/verify.mjs`
с ненулевым кодом возврата, срабатывает **только у того, кто это запустил**:
к сборке страницы не подключено, в CI не подключено.

Практический смысл границы: если завтра кто-то поправит пример в
`src/scenarios.md` и не откроет этот файл, красного не будет нигде — ни
локально, ни на pull request.

Подключение к CI потребовало бы поднимать API в пайплайне (прогон идёт против
живого сервиса) и правки `scripts/ci/`, то есть чужой зоны. Не сделано
сознательно и названо здесь, а не подразумевается: защита с необъявленной
границей успокаивает сильнее, чем защищает.

## 1. Сборка

```bash
cd docs-site
npm ci && npm run build
```

Прочитать вывод: число операций и кодов ошибок должно совпадать с контрактом,
а строка «Адрес в контракте» — сказать, совпадает он с адресом стенда или
расходится. Сборка падает сама, если в контракте появился код, нигде, кроме
перечня, не объяснённый.

## 2. Обе ветви адреса

```bash
cd docs-site
npm run build                                   # адрес стенда = адрес контракта
API_BASE=http://localhost:18110 npm run build   # адреса расходятся
```

Первый прогон: `spec-notice` в `dist/index.html` быть **не должно**. Второй:
должно быть, и в тексте — оба адреса, стенда и контракта.

Условная отрисовка — две дороги, и показать одну легче, чем обе. Само условие
сравнивает адрес стенда с **фактическим** `servers` контракта, а не с
константой: константа рано или поздно разойдётся с контрактом и начнёт врать
в обе стороны сразу.

## 3. Прогон примеров — дважды

Нужен живой API. Команды берутся **из собранной страницы**, а не из
`src/scenarios.md`: проверять надо то, что скопирует читатель.

```bash
cd docs-site
node tools/extract.mjs                       # блоки из dist/scenarios.html
node tools/run.mjs first.txt
node tools/run.mjs second.txt
node tools/verify.mjs first.txt second.txt
```

`verify.mjs` делает две разные проверки и возвращает ненулевой код при любом
расхождении:

- **соответствие** — ответ совпал с кодом, помеченным в блоке строкой
  `# ожидается NNN`. Это ловится **первым** проходом;
- **устойчивость** — второй проход ответил тем же, что первый.

Одна другую не заменяет. Пример с прибитым ключом отвечает 200 в обоих
проходах: устойчив и при этом сломан, потому что страница обещает 201.

Правило устойчивости обязательно для блоков, **создающих или потребляющих
состояние стенда**; признак — не код ответа: `400` на длинный ключ не зависит
ни от чего, а `409 idempotency_key_reuse` держится целиком на соседнем блоке,
хотя оба отказы.

### Разметка блоков страницы сценариев

| Блоки | Роль |
|---|---|
| создание с `$KEY`, `$PAYMENT_ID`, `$DONE_ID`, экзотический ключ, суммы-триггеры | **создают** состояние |
| повтор → 200, 409 `idempotency_key_reuse`, статус, чужой мерчант, отмена, список, дубль ключа | **потребляют** состояние |
| маршрут (404/405), отсутствующие заголовки, длинный ключ, битый JSON, невалидные поля | ни от чего не зависят |

## 4. Самостоятельность блока

Отдельный вопрос, прогоном не проверяемый: **что вернёт блок, если выполнить
только его**. Читатель редко проходит страницу целиком — он копирует тот блок,
который решает его задачу сейчас.

Блоки-потребители в одиночку отвечают не то, что обещано (шаг 3 без шага 1
вернёт 201 вместо 409). Это допустимо, но обязано быть сказано на самой
странице, а не только здесь: читатель чек-листа не видит.

## 5. Глазами

```bash
cd docs-site
npm run serve      # раздаёт dist на http://localhost:8082, не завершается
```

Открывать страницу **по http**, а не файлом с диска: с диска браузер запрещает
запрос к `openapi.yaml`, справочник не рисуется и консоль краснеет — это
ожидаемо и о качестве страницы ничего не говорит.

Смотреть: таблицы контракта не разъехались, кириллица цела, ширина 390 px
не ломает вёрстку, в сетевом логе только свой хост (страница обязана работать
без интернета).

**Консоль пуста только при раздаче нашим сервером или из образа.** Сторонний
статический сервер вернёт 404 на `/vector/registry/*` — это Scalar стучится
в свои облачные подсказки, и гасят их `serve.mjs` и `nginx.conf`, отвечая
пустым `204`. Увидели такие 404 — вы раздаёте не тем сервером.

Остановить: `Ctrl+C`.

## 6. Образ

Собирается **из корня репозитория**: контекст сборки — весь репозиторий,
потому что странице нужен `openapi/openapi.yaml` и `design/tokens.css`.

```bash
cd ..
docker build -f docs-site/Dockerfile -t psp-docs .
```

Проверка рантайма — одной командой, контейнер сам завершается:

```bash
docker run --rm psp-docs sh -c 'command -v node || echo "node: нет"; ls usr/share/nginx/html'
```

Ожидается `node: нет` и список статики, в котором нет `node_modules` —
в рантайме только nginx и собранная страница (R3). Числа файлов здесь нет
намеренно: оно устареет на первой же правке, а проверяется не количество.

Путь написан от корня контейнера без ведущего слэша намеренно: в агентских
сессиях этого репозитория хук `guard-scope` разбирает текст команды и считает
абсолютный путь попыткой записи наружу — команда с `/usr/share/...` до Docker
не доедет. Рабочий каталог в образе nginx — корень, так что запись без слэша
равнозначна.

Раздача из образа, если нужна глазами:

```bash
docker run --rm -p 8090:8082 psp-docs      # не завершается, Ctrl+C для остановки
```

Порт **не 8082**: если стенд поднят (а шагу 3 он нужен), 8082 уже занят
сервисом `docs` из `compose.yaml`, и запуск упадёт с «port is already
allocated». Любой свободный порт годится — внутри контейнера всегда 8082.
