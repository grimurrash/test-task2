## Решения

### Р1. Копия заведена, ветка переименована под текст задачи

`git worktree add` прошёл без отказа хука. Постановка называла ветку

задача, а не пересказ.

Ещё одно расхождение: постановка утверждала, что PR #48 не слит. На момент старта
`origin/main` действительно был на `656c7f0` без `frontend/`, но PR #48 влился

### Р2. Приёмка задания — вердикт «беру», пять вопросов

Названо расхождение, которое я не имею права разрешить сам: задача требует

Дефекты описаны в `docs/reviews/breaker.md` и уйдут комментарием в #15; issues

Один пункт остался без ответа и потому не сделан — 3(в): мутации **продуктового

### Р3. Свой экземпляр сервиса вместо чужого

На `:8080` живёт контейнер `psp-api`, собранный в 16:42 из неизвестного коммита

Поднял свой API на `:8095` из `004a6cf` и прод-сборку песочницы на `:5175`
с `VITE_API_BASE=http://localhost:8095`. Прод-сборку, а не `vite dev`: A10
проверяет то самое место, где dev и прод расходятся.

Проверил, что сборка та, что нужна: три находки ревью #47 (битый URL, `__proto__`,
предел тела) на ней уже починены.

### Р4. Главное методическое решение — колонка «доехало»

Формат строки из задачи («что пробовал · команда · ожидание · факт · вердикт»)
не оставляет места для вопроса, достигла ли атака проверяемого места. Добавил
шестую колонку. Она сразу окупилась трижды:

- **гонка через `fetch`** (25 раундов, идеальный результат) — `undici` держит пул
  соединений и сериализует запросы; сервер никогда не видел их одновременно.
  Переделано на сырые сокеты с телом, разрезанным пополам, и паузой 150 мс:
  в паузе четыре запроса физически внутри сервера. Только после этого «устояло»
  что-то значит;
- **дубль `X-Merchant-Id`** — мой сокетный клиент дал `ECONNRESET`; через `curl`
  сервис штатно отвечает 400. Барьер был на моей стороне;
- **мутация M5** (правило сумм по строке вместо остатка) показала «набор
  не различает» — а на деле `"1".slice(-2)` равно `"1"`, поведение не изменилось.
  Мутация не доехала. Заменена на M11, та покраснела дважды.

Без этой колонки в отчёте стояло бы три ложных «устояло» и одна ложная дыра
в наборе.

### Р5. Мутации ставились по строке, которая держит свойство

Метод из промпта 2. Не «поломать что-нибудь», а найти строку-держатель и убрать
именно её: `fingerprintOf` для «того же тела», `#expired` для TTL, `#slot` для
скоупа мерчанта, `headerValue` для дублей заголовка. Из 18 мутаций 16 покраснели,
одна не доехала (M5), одна мутировала мёртвый код (M18), и ровно одна прошла
набор насквозь — M17, `description` хранится обрезанным. Её наблюдаемость
подтверждена запуском мутантной сборки рядом с продуктовой.

## Замечания по обвязке, встреченные по дороге

Не продукт и не моя зона, но три отказа стоили времени, и один из них выглядит
шире, чем открытая #43.

`guard-scope` отклонил три безобидные команды:

1. `curl -w 'GET /v1/payments/%%00 -> …'` — путь в **данных** формата вывода принят
   за путь в команде (это #43, PR #53);
2. регулярное выражение `/transfer-encoding:\s*chunked/i` внутри heredoc — то же самое;
3. `cd <репозиторий>/backend && npm test > ../.qa-tmp/backend-test-baseline.log` —
   путь **внутри** репозитория. Похоже, относительный путь разворачивается
   от корня проекта, а не от каталога, в который команда сделала `cd`.

Третий случай интереснее первых двух: если резолвинг действительно игнорирует `cd`,
то симметричный случай — `cd` наружу и относительная запись — проверку пройдёт,
хотя писать будет за пределами репозитория. Сам это не проверял: проверка означала
бы запись наружу, то есть ровно то, чего граница не разрешает. Гипотеза для сессии
обвязки, не находка.

Обход, который использовал: абсолютные пути внутри репозитория и инструмент `Write`
вместо heredoc.
