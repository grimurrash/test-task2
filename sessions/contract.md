## Решения контракта

| Решение | Обоснование |
|---|---|
| `GET /v1/payments` → `{"payments": [...]}`, сортировка `created_at` по убыванию, без пагинации | Решение сэра. Обёртка расширяема без слома клиентов; песочнице не нужно сортировать самой |
| **Вся валидация тела** (`amount_minor`, `currency`, `order_id`, `description`) → **422** `validation_failed`, карта всех нарушений разом в `details.errors`; **400 — только заголовкам** (`merchant_id_required`, `invalid_merchant_id`, `idempotency_key_required`) | Решение сэра, в два шага. Сначала 422 назначался только `order_id`/`description` (F8/F9 диктовали 400 с кодами на поле) — получалась асимметрия трёх режимов. Сэр её отверг; разбор стандартов: RFC 9110 — 400 «не разобрали запрос», 422 «разобрали, данные не проходят»; школа Stripe/Google — всё 400 с кодом поля; школа GitHub/Laravel/Rails — 422 + карта. Выбран единый 422: один механизм, все нарушения одним ответом. Коды `invalid_amount`/`invalid_currency` сняты, enum — **восемь** кодов. Пересматривает PRD F8/F9 — правка PRD догонит (прецедент F17/F18), решение зафиксировано комментарием в #9 |
| Чужой платёж по верному `id` (GET и cancel) → **404** `payment_not_found` | Решение сэра. Скоуп мерчанта на всех эндпоинтах, существование чужого ресурса не утекает; согласуется с F6 и F16 |
| `Idempotency-Key`: строка 1–255, пустое значение = отсутствие → `idempotency_key_required`; формат не навязывается | Решение сэра. Бэкенду и песочнице — одинаковая граница; кнопка генерации даст UUID, но контракт не сужает |
| Правило тестовых сумм записано как `amount_minor % 100 == 1 / == 2` с явной оговоркой про суммы `1` и `2` | Требование задачи (продукт, 2026-08-25) — дословно; иначе короткие суммы бэк и фронт растолкуют по-разному |
| `security: []` на корне + комментарий в файле | Аутентификации нет по замыслу (PRD «Не входит»); `X-Merchant-Id` — идентификация, смоделирован обязательным header-параметром, а не security-схемой, чтобы кодогенерация фронта видела его как обычный заголовок. Заодно закрывает правило `security-defined` линтера |
| `description` и `status_reason` в ответе — обязательные nullable-поля (`type: [string, "null"]`) | Кодогенерации проще: поле всегда есть, отсутствие значения — `null`, а не «может не быть ключа». Для `status_reason` это прямо F18 |
| `amount_minor`: `minimum: 1`, `maximum: 9007199254740991` | F8: строго больше нуля и в границе безопасного целого (2^53 − 1) — граница видна машинно, а не только текстом |
| `details` в конверте ошибки — необязательный объект | 5.4 задаёт форму, но не обязательность; жёстко закреплён только `details.errors` у `validation_failed` и `details.status` у `payment_not_cancelable` (примерами) |
| `redocly.yaml`: `no-server-example.com: off`, `info-license: off` | localhost:8080 — согласованная проджектом константа, внешнего хоста нет по замыслу; лицензия репозиторию не назначена, выбор — вне контракта. Оба отключения с комментариями в конфиге |

# Задача #64 · «Символы» против кодовых единиц — правка не понадобилась

25 августа 2026. Вердикт приёмки — «нужны ответы»: посылка задачи
(«стандартный `maxLength` меряет кодовые единицы UTF-16») оказалась неверна —
по JSON Schema (RFC 8259) длина строки считается кодовыми точками, и ajv@8
бэкенда меряет точки, а их runtime — `.length` (единицы). Расходились два
механизма бэкенда, не контракт с кодом. Ранис закрыл развилку в пользу точек
по трём независимым основаниям (текст стандарта, моя проверка по lock-файлу,
измерение бэкендера) — «символы» в контракте оказались точным термином
стандарта, файл не тронут, #64 переадресована бэкенду как дефект кода.
Побочная находка важнее самой задачи: валидация запросов у бэкенда написана
руками мимо схемы — слепое пятно автоматической сверки A7.

# Задача #86 · Дублирующиеся заголовки рвут идемпотентность

25 августа 2026, из дефекта #73 (QA): запрос с двумя одинаковыми
`Idempotency-Key` и честный повтор одним дают два платежа — Node склеивает
дубли в «K, K», повтор в этот ключ не попадает. Решение продукта внесено
как есть: заголовок, присланный более одного раза (повтором, значениями
через запятую, именами в разном регистре), отклоняется — ключ → 400
`invalid_idempotency_key`, мерчант → 400 `invalid_merchant_id`; проверка
первым слоем, до разбора тела (порядок из #32). Новых кодов нет.

Решения формулировки (названы в приёмке):

| Решение | Обоснование |
|---|---|
| Значение ключа с запятой отклоняется как склейка дублей | Инфраструктура склеивает дубли до кода — реализация, получающая заголовки склеенными, иначе не может исполнить правило; текст покрывает обе точки зрения («вижу два заголовка» и «вижу значение с запятой»). У мерчанта запятая и так вне набора |
| Причина продукта перенесена в текст заголовка | Ключ — идентификатор намерения; два значения = клиент не знает, какой запрос повторяет; выбрать за него — угадать ценой второго платежа. Контракт с «почему» экономит интегратору спор |
| Обновлены ячейки «Когда» таблицы кодов | Иначе таблица врёт относительно описаний заголовков; трактовка границ названа в приёмке |

**Дополнение по ревью #86 — запятая.** Ревью проджекта показало: следствие
«значение с запятой отклоняется» сужало множество ключей, оставаясь выводом
из абзаца. Из трёх вариантов выбран второй (набор символов явно):
`pattern: ^[A-Za-z0-9._-]{1,255}$` — алфавит `X-Merchant-Id`. Правило стало
проверяемым схемой; составные ключи — через `._-`; запятая и пробелы вне
набора (закрыт и «ключ с пробелами по краям» из форы ломателям). Цена —
гипотетический ключ вида `order,attempt` получает 400 — названа в решении
([#86, комментарий](https://github.com/grimurrash/test-task2/issues/86#issuecomment-5412928623)).
Против варианта 3 (дубли до склейки) — довод проджекта: за склеивающим
прокси правило неисполнимо.

# Задача #94 · Коды маршрутизации — контракт догоняет поведение

25 августа 2026, из дефекта #74 (QA). Сервис отвечает `not_found` и
`method_not_allowed` со статусами 404/405, которых в контракте не было, —
A7 нарушался любым запросом мимо описанных путей. Бэкендер сам отверг
обход «врать payment_not_found на чужой метод»; согласен — код ошибки
есть утверждение. Внесено: enum 10 → 12, подраздел «Маршрутизация»
в формате ошибок, две строки таблицы; разница двух 404 — «нет адреса»
(путь) против «нет платежа или он чужой» (ресурс) — прописана и в таблице,
и в подразделе. 405 к каждой операции не приписывается: OpenAPI не выражает
«все остальные методы», правило дано один раз на всё API. Сверка по п. 3
задачи: тело только у создания (покрыто `malformed_request`), 5xx за
границей контракта (#32); вопрос бэкендеру о служебных маршрутах (health)
задан в приёмке — не блокирует. Выполнено одним PR с #86 по разрешению
проджекта, отдельным коммитом.

## Ревью документации: «вернуть», четыре находки — все справедливы

Проверяющий (роль «документация», постоянная пара к контракту) вернул PR #90
чтением текста, не командами; все четыре находки подтвердились по файлу
и починены одним коммитом с решениями проджекта:

| Находка | Починка |
|---|---|
| Правило 405 противоречит CORS: `OPTIONS` не описан → по букве 405, по CORS 204; честный реализатор сломал бы preflight песочницы | Явная фраза в «Маршрутизации»: `OPTIONS` под оба правила не попадает, отвечает 204 на любой путь по разделу CORS (решение проджекта) |
| Место маршрутизации в порядке проверок не задано: `POST /v1/nope` без заголовков — 404 или 400? | Маршрут — нулевой слой, вписан в строку порядка: маршрут → заголовки → разбор тела → поля; «правила маршрута нельзя применить к маршруту, которого нет» (решение проджекта, совпало с реализацией) |
| Обзор «Идемпотентность» обещал «непустую строку 1–255», не зная набора и однократности | Набор и однократность — в первый абзац обзора одной строкой |
| Тело PR: «новых кодов нет» — устарело после объединения задач | Тело PR переписано |

**Урок, записанный как привычка** (второй случай после #51/#58): правка
ложится в частные места, обзорный раздел продолжает обещать старое —
после любой правки перечитывать обзор, он врёт первым. И метод проверяющего
на заметку: все находки из чтения, ни одной из вывода команд — его зоне
(сборке страницы) правка не грозила, поэтому он проверял текст.

## Срочный откат набора символов ключа — конфликт с принятой починкой #75

Сразу после слияния #90 проджект обнаружил: `pattern ^[A-Za-z0-9._-]{1,255}$`
отменяет закрытую починку #75 — ломатель добился, чтобы ключ до 255 символов
принимался независимо от письменности («формат не навязывается»), бэкенд
починил, приёмка прошла, тесты стоят (255 кириллических → 201). По новому
контракту эти тесты обязаны падать — слияние молча вернуло найденный дефект.

Решение проджекта (признал ошибку своей рекомендации из ревью сам): набор
откатить, однократность оставить. Внесено: `pattern` снят, «формат
не навязывается» возвращён в описание параметра и в обзор, следы набора
вычищены из таблицы и примеров (обзоры перечитаны — привычка действует).

Хвост отката, названный вслух, а не умолчанный: без набора реализация,
получающая заголовки уже склеенными, не может отличить дубли от законного
ключа с запятой. Контракт теперь требует различать дубли **до**
инфраструктурной склейки (в Node — `rawHeaders`; наша реализация так
и делает) и прямо говорит, что склеивающий прокси перед API ломает правило —
это ограничение развёртывания. Фактически это вариант 3 из ревью #90,
переоценённый после конфликта с #75: цена «неисполнимо за прокси» оказалась
меньше цены «откат принятой починки». `X-Merchant-Id` не тронут — его набор
задан продуктом (F7a), и склейка его дублей невалидна по-прежнему.

# Задача #113 · Оговорка про прокси: граница и цена

25 августа 2026, из замечаний повторной проверки #109 (не держали слияние).
Две правки: (1) фраза «исполнить правило не может — не ставьте прокси»
сужена до фактической границы и досказана формулировкой проверяющего:
за склеивающим прокси ломается ровно обнаружение дублей заголовка — дубли
склеятся в «K, K», запрос пройдёт как обычный, честный повтор с ключом K
в него не попадёт, **два платежа вместо одного**; остальные гарантии
не затронуты. (2) Ячейка таблицы про однократность перестала обещать
безусловное — условие «дубли видны только до склейки» внесено в ячейку
(четвёртый случай болезни «частное правило внесли, общее место отстало»,
на этот раз таблица отстала от описания).

**Урок дня, дословно от проверяющего: оговорка, скрывающая цену, хуже
отсутствующей — она успокаивает.** Моё «не может исполнить правило» звучало
честностью, но прятало последствие — двойное списание, ради которого весь
проект. Оговорка обязана называть, что ломается и чем это грозит.

Дубль оговорки в README — зона devops, проджект передаёт владельцу сам.

**Итог:** принята с первого захода — PR #114 слит, #113 закрыта проджектом.
Формулировка проверяющего внесена дословно, проверял он же.
