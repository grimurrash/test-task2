# Рустем-180 — задача #180

## Задание (дословно, из тикета)

`[требования] шесть непокрытых хвостов: F20, U4, U7, A4, A7, A8`. Аудит показал:
50 из 56 требований PRD подтверждены прогоном полностью, 6 — частично.
Задача закрывает ровно эти шесть хвостов и ничего сверх них. Источник истины —
`docs/product/PRD.md`.

Общее правило приёмки: на каждый хвост нужен тест, **который покраснеет при
нарушении требования**. Обратную проверку исполнитель делает сам: ломает
поведение, показывает красный, возвращает, показывает зелёный; оба вывода —
в этот журнал. «Тест есть» доказательством не считается.

## Отступление от обычного цикла (решение сэра, причина — лимит токенов)

1. Ревью плана — **ровно один** агент-ревьюер вместо трёх. Codex на ступени
   ревью плана не запускается вовсе.
2. Ревью результата — **только** `codex exec review --base main -o <вердикт>`.
   Агентов-ревьюеров на этой ступени ноль.

Что не отменяется: пустой / упавший по таймауту / `unavailable` вердикт codex —
это **отсутствие внешней линзы**, а не «чисто»; так и пишется в PR и в рапорт.
Замечание codex нельзя проигнорировать молча: либо правка, либо письменный отказ
с обоснованием.

### Чего сделать не удалось, и почему — это не «всё хорошо»

> **ЭТОТ ВЫВОД ОКАЗАЛСЯ НЕВЕРНЫМ. Оставляю его на месте вместе с разбором:
> вычёркивать собственную ошибку — значит прятать её.** Что было измерено
> и что из этого следовало на самом деле — сразу под блоком.

**Полный прогон на чистом клоне (исход 0) и прогон со сломанной приёмкой
(исход 1) в этой среде выполнить нельзя.** Демон Docker здесь не тянет образы:

```

psp-backend:local                      есть, но собран 33 часа назад —
                                       из старого кода, моих тестов не содержит
```

Строку про `psp-backend:local` поправил после замечания координатора: сперва
я написал «отсутствует», и это была неправда — образ есть, я обрезал вывод
`docker image ls` через `head` и не заметил. Вывод от этого не меняется
(старый образ доказательством не является), но неверная строка в честном
рапорте остаётся неверной. Отсюда же следует ловушка, в которую здесь легко

Порядок событий здесь стоит записать точно, потому что он не случаен:
**неверная строка в рапорте, будучи исправленной, вытащила настоящий дефект.**

с очень длинной немой головой: минуты без единой строки прогресса, потом успех.

Мои же наблюдения ложились на это без противоречия и должны были насторожить:
«висел на resolve image config пятнадцать минут» описывает медленного демона
не хуже, чем мёртвого. Я выбрал одно объяснение из двух и не проверил выбор —
хотя проверка стоила одной команды, оставленной доработать.

Класс тот же, что и с обрезанным `head`: наблюдение подменено выводом.
Разница в том, что здесь вывод попал в блокирующий рапорт координатору
и в тело PR как факт.

**Следствие для скрипта, а не только для совести.** `BUILD_TIMEOUT` я добавил
верно — зависание не давало ни одного из трёх исходов. Но предел, подобранный
под быструю сеть, теперь сам может выдать «проверять было нечего» на честной
медленной сборке, то есть повторить мою ошибку машинно. Поэтому сообщение
переписано: упёрлось во **время**, о самой сборке отсюда не известно ничего,
первое действие — поднять предел. Значение задаётся снаружи и в шапке скрипта
названо.

### Находка: P1, уборка идёт не из того каталога

> Once the stack starts, `compose.yaml` is under `$CLONE_DIR/repo`, but cleanup
> runs `docker compose down` from `$CLONE_DIR`. Compose therefore finds no
> configuration, and the suppressed error leaves containers, networks, and
> volumes running while the clone is deleted.

**Первая половина — правда, и это мой недосмотр.** В `cleanup()` стоял
`$CLONE_DIR`, тогда как клон лежит в `$CLONE_DIR/repo`. Исправлено.

**Вторая половина — на этой версии Compose не воспроизводится, и я называю это
прямо, а не принимаю на веру.** Проверено живым стендом, а не рассуждением:

```
Docker Compose version v2.34.0-desktop.1

поднято: psp-teardown-live-probe-1
-- down ИЗ РОДИТЕЛЯ (как было в первой редакции) --
 Network psp-teardown-live_default  Removing
 Network psp-teardown-live_default  Removed
код: 0
осталось:
```

То есть Compose v2 разрешает проект по имени `-p` и без файла конфигурации:
контейнеры и сеть снимаются, утечки нет. На Compose v1 — была бы.

**Правку оставляю.** Не потому, что «ревьюер сказал», а потому что она снимает
зависимость от версии Compose и от того, что уцелело на диске: уборка идёт
из каталога клона, а если его уже нет — по метке `com.docker.compose.project`.
Отказ уборки перестал глушиться молча.

Вторая модель — не старшая: путь она указала верный, последствие завысила.
Обе половины записаны.

Других находок в вердикте нет; `[P1]`/`[P2]` в полном логе — образцы формата
из собственного шаблона codex, не находки по этому диффу.

## Отказы механизмов за задачу

Три, все ложные, все по одной причине: `guard-scope` принял за путь наружу
текст **внутри** команды, а не саму команду.

1. `cd backend && ... cd ../frontend` → «Заблокировано… Путь: ../frontend».
   Обошёл абсолютными путями через `npm --prefix`.
2. `grep ... | sed "s/describe('//;s/', () => {//"` → «Путь: //;s/,».
   Обошёл без `sed`.
3. heredoc с текстом правки, где в комментарии стояло `design/README.md`
   → «Путь: /». Обошёл файловыми инструментами.

Работать это не помешало ни разу, но три обхода на одну задачу — цена,
и она повторится у следующего исполнителя.
