### Решения по ходу

**Стенд собирал сам, не ждал.** #49 смотрел dev-сборку на `vite`; проверяющий
увидит nginx-статику из образа. Собрал `psp-sandbox:qa-ui` из `frontend/Dockerfile`
и поднял на `:18091`. Позже, когда `compose.yaml` доехал в `main`, синхронизировал
ветку и поднял весь стек одной командой на `:18110/:18111/:18112`.

**Прокси управляемых отказов.** Без него не проверить ничего из списка
«поведение при отказе бэкенда»: живой локальный API не рвётся и не тормозит.
Поставил между браузером и API свой прокси (`:18099`) с режимами «оборвать
создание», «оборвать отмену», «задержать», «осиротить ответ». Кода сервиса
он не касается — это сетевое условие. В каждой итерации, где он работал,
это сказано вслух.

**Промах, стоивший итерации.** Первый вариант прокси задерживал **запрос**,
а не ответ. Клиент отваливался по таймауту раньше, чем прокси доходил до чтения
тела, — до API не долетало ничего. Итерация выглядела проведённой, а проверила
мой прокси. Поймал по колонке «доехала»: платежей на сервере `8 → 8`.
Переписал прокси (режим `orphan`: запрос уходит в API, ответ до браузера
не доходит) и переиграл — тогда и получил самый сильный результат сессии (И10).

**Порядок проверки чужой передачи.** Находку про `U+202E` владелец передал
как чужую и попросил подтвердить независимо. Не принял на слово: сначала
прочитал платёж обратно через API и напечатал кодовые точки — убедился,
что `0x202e` доехал до хранилища; потом замерил `getBoundingClientRect()`
по каждому символу и получил убывающую координату `x`. Только после этого завёл #76.

## Второй заход: ревью чужой правки вместо поиска дефектов

Пауза на поиск дефектов продукта осталась в силе, задачи сменились дважды.

### Ревью PR #53 — правка `guard-scope` по задаче #43

Владелец задачи перевёл меня в приёмщики правок Никиты, объяснив выбор так:
ломатель не знает замысла и не сочувствует решению. Просьба была смотреть
**код**, а не только вывод, и искать, **чего в правке нет**.

**Вердикт: вернуть.** Одна блокирующая причина.

Прежде чем возвращать, измерил соразмерность, иначе вердикт был бы несправедлив:
на одном корпусе `main` даёт 14 расхождений, ветка — 9. Пять случаев починены,
два из них — настоящие дыры (`python3 - <<'PY'` и `env -i --` перед
интерпретатором писали наружу на `main`), один — блокер с корнем
(`chmod -R 777 /` на `main` **проходил**). Ни один работавший случай не сломан.
Правка — чистое улучшение; возвращал не её, а утверждение, которое вместе
с ней уехало бы в задачу и в `docs/HOOKS.md`.

**Блокер (Б1).** Тело PR называет источники томов docker единственным местом,
где сужение стало бы дырой, и заявляет, что они проверяются как раньше. Это
верно про разбор путей и неверно про хук: **разбор до тома не доходит**. Ранний
гейт ищет намерение записи по строке, и у `docker run -v <наружу>:/data alpine`
такого признака нет — команда проходит. Отказ появляется только когда в строке
случайно оказывается `rm`: во всех четырёх docker-случаях авторского набора
стоит `--rm`, и он открывает гейт подстрокой внутри флага.

**Едва не завысил находку — и это записываю отдельно.** Первой мыслью было
«тест декоративен». Вместо того чтобы это написать, проверил мутацией: вырезал
возврат путей хоста (`return True, host` → `return True, []`). **Три теста
покраснели** — тест различает, он проверяет ровно то, что заявляет. Не видит он
другого: **достижимости**. Это не «проверка ни о чём», а слепое пятно в одном
измерении, и разница существенная — обвинить автора несправедливо дороже
пропущенной находки.

**Поправка от коллеги, изменившая диагноз.** Кристина (#15) прогнала свою
половину и прислала второй вход в ту же дыру: `rm` не во флаге, а **внутри
аргументов контейнера** — `sh -c "rm -rf /data/x"`. Проверил дословно,
подтвердилось; `mv` и `touch` там же тоже открывают гейт, а `cat` — нет.

Это не приписка, а уточнение причины. Я назвал виновником совпадение `\brm\b`
с флагом `--rm` — верно, но узко: звучит как «поправьте регулярку», автор бы
её поправил, и дыра осталась бы. Точная формулировка: **ранний гейт ищет
намерение записи по всей строке, включая ровно тот участок, который сужение
по docker объявляет не имеющим отношения к границе хоста.** Дополнение
опубликовал отдельным комментарием, авторство второго входа назвал.

Заодно поправил и своё требование к набору: я написал «достаточно команды
без `--rm`» — это закрыло бы один вход из двух. Её вариант правильнее:
`docker run -v <каталог хоста>:/data alpine`, без глаголов вообще.

**Про порядок работы.** Кристина сняла свою претензию ко мне раньше — на команде,
которая отказывала по постороннему признаку: сошёлся вывод, а не механизм.
Я не взял снятие на слово и прогнал дословно; она не стала защищать свой вывод
и перепроверила мой. Нужны были обе половины.

### Проверка исполнимости `README.md` и `REPORT.md` (#18)

Критерий владельца: считать, сколько раз пришлось открыть что-то за пределами
документа. Автор такую проверку провести не может — он открывает соседний файл
не глядя и не засчитывает это.

**Первым делом назвал изъян метода применительно к себе:** я не чистый читатель,
четвёртый час в проекте, помню порты и то, что адрес API вшивается на сборке.
Поэтому считал не «сколько открыл я», а «сколько раз документа, прочитанного
в одиночку, не хватает» — и всё равно назвал свой счёт нижней границей.
Чтобы приблизиться к чистоте, взял **настоящий свежий клон** из `origin`
в отдельный каталог, а не рабочую копию.

**Счёт: 1.** `scripts/acceptance.sh` — README велит сменить порты при конфликте,
следующим разделом даёт `bash scripts/acceptance.sh` и нигде не говорит,
как направить его на новый порт. `BASE_URL` существует, но задокументирован
в шапке скрипта.

**Главное в отчёте — не цифра.** Обе проверки из раздела «Проверка, что всё живо»
прибиты к `8080` — тому порту, который двумя разделами выше README предложил
освободить как занятый. Создал платёж-маркер только на своём стеке: `18080` —
один платёж, `8080` — ноль. Разные сервисы, а проверка отвечала `200`.
Дальше погасил свой стек целиком и повторил обе команды дословно: живость `200`,
приёмочный сценарий — **«Приёмка пройдена: расхождений с заявленным поведением
нет.»** Стека нет.

Читатель при этом **не открыл ничего** — счёт засчитал бы ему ноль.

Отсюда замечание к самому критерию, которое считаю ценнее находки: он ловит
**неполноту** документа и слеп к его **неверности**. Здесь он поставил бы почти
отличную оценку тексту, чей раздел проверки инертен. Тот же сюжет, который
в `REPORT.md` назван главным провалом проекта, — только стоит он на входной
странице.

**Утверждение «предусловий нет, кроме Docker» держится наполовину:** подъём
и `docker compose run --rm backend-test` — да (187 тестов, 0 падений), но
проверкам нужны `curl` и `bash`, а разделу про обвязку — `python3`.

Ложную находку снял по дороге третий раз за сессию: `jq` в `acceptance.sh`
упомянут как **не** требующийся.

### Регресс #92 — измерением, а не чтением диффа

Стенд поднят заново из своей копии на `db331df`, образы пересобраны, три
предельных по контракту платежа засеяны с нуля: `order_id` 64 символа,
`description` 512 без разделителей, `amount_minor = 9007199254740991`.
Все три приняты сервером (201) — то есть атака доехала.

| Ширина | Было (мой замер до фикса) | Стало |
|---|---|---|
| 375 | **33px**, виновник `.status` карточки `ORD-BIG-AMOUNT` | **0**, `offenders: []` |
| 768 | 0 | 0 |
| 1280 | **76px**, виновники `.minor.mono` и `.status` | **0**, `offenders: []` |
| 1440 | **76px**, те же два | **0**, `offenders: []` |

Скриншот на 375 показывает, что происходит вместо вылета: сумма
и `9007199254740991` переносятся, бейдж статуса уходит на свою строку,
64-символьный `order_id` ложится в две строки, 512-символьное описание
обрезается тремя строками с «показать целиком».

**Фикс оказался шире находки.** Я сообщал только про вёрстку. В `money.ts`
починено ещё и то, чего я **не находил**: деление на 100 через `double` теряет
копейку на границе безопасного целого — `9007199254740991 / 100` даёт
`…409.90625`, то есть «,90» при минорных «…91». Проверил на живом экране:
`90 071 992 547 409,91 RUB`. Копейка на месте.

**И способ решения лучше, чем я просил.** Я указывал на конкретную строку
карточки; перенос вынесли правилом на `.payment` целиком с объяснением в коде —
«поле, добавленное завтра, получит его само, а не по памятке». Это ответ
не на мою находку, а на вопрос из задачи «единственное ли это поле»: закрыт
класс, а не второй случай после первого.
