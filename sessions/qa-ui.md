## Ход работы

### Задача найдена: #63, а не #15

`gh issue list --label role:qa` на старте показал одну #15 — она чужая
(приёмка исполнителем написана, копия `.worktrees/psp-qa`, зона — HTTP API).
Моя задача **#63** появилась позже, её принёс владелец сообщением. Ветку
в задаче назвали `feature/qa-sandbox`, прямая постановка сэра — `feature/qa-ui`.
Оставил второе (приоритет 1 — прямая просьба сэра), расхождение назвал
в приёмке и предложил переименовать по одному слову.

### Решения по ходу

**Стенд собирал сам, не ждал.** #49 смотрел dev-сборку на `vite`; проверяющий
увидит nginx-статику из образа. Собрал `psp-sandbox:qa-ui` из `frontend/Dockerfile`
и поднял на `:18091`. Позже, когда `compose.yaml` доехал в `main`, синхронизировал
ветку и поднял весь стек одной командой на `:18110/:18111/:18112`.

**Прокси управляемых отказов.** Без него не проверить ничего из списка
«поведение при отказе бэкенда»: живой локальный API не рвётся и не тормозит.
Поставил между браузером и API свой прокси (`:18099`) с режимами «оборвать
создание», «оборвать отмену», «задержать», «осиротить ответ». Кода сервиса
он не касается — это сетевое условие. В каждой итерации, где он работал,
это сказано вслух.

**Промах, стоивший итерации.** Первый вариант прокси задерживал **запрос**,
а не ответ. Клиент отваливался по таймауту раньше, чем прокси доходил до чтения
тела, — до API не долетало ничего. Итерация выглядела проведённой, а проверила
мой прокси. Поймал по колонке «доехала»: платежей на сервере `8 → 8`.
Переписал прокси (режим `orphan`: запрос уходит в API, ответ до браузера
не доходит) и переиграл — тогда и получил самый сильный результат сессии (И10).

**Порядок проверки чужой передачи.** Находку про `U+202E` владелец передал
как чужую и попросил подтвердить независимо. Не принял на слово: сначала
прочитал платёж обратно через API и напечатал кодовые точки — убедился,
что `0x202e` доехал до хранилища; потом замерил `getBoundingClientRect()`
по каждому символу и получил убывающую координату `x`. Только после этого завёл #76.

### Что не подтвердилось — ложные находки, снятые до заведения

Записываю, чтобы не выглядеть точнее, чем есть.

1. **Подпись формы про тестовые суммы.** Заподозрил противоречие с контрактом:
   контракт предупреждает против чтения «оканчивается на 01», а форма пишет
   «копейки 01». Проверил — противоречия нет: «копейки» и есть `amount_minor % 100`,
   сумма `1` под подпись попадает верно. Issue не завёл.
2. **Обрезанный пример на странице документации.** Блок с телом
   `-d '{"amount_minor":'` выглядел как оборванный копипастой. Посмотрел исходный
   HTML — это намеренно битый JSON для показа `400 malformed_request`, кавычки
   сбалансированы, копируется и выполняется. Issue не завёл.

### Разбирательство с откатом в общей копии

Владелец спросил, моё ли: в индексе общей копии 707 удалённых строк, среди них
`compose.yaml` и чужой журнал, плюс след `p7-inject.log`. Ответил «нет»
с доказательством, а не по памяти: в моей копии `git status --porcelain` —
одна строка `?? sessions/qa-ui.md`, коммитов ноль; в общей копии за сессию
сделал ровно два read-only действия (`gh issue view` и `git worktree add`);
скрипты инъекций не запускал ни разу; `p7-inject.log` на диске нет.
Ничего не восстанавливал и не прибирал — владелец просил не трогать до выяснения.
Позже то же обвинение пришло вторым каналом от продукта — поправил и там:
принимать чужую атрибуцию молча значит закрепить её в отчёте.

Продукт передал распоряжение сэра: новых заходов на взлом не начинать, новых
issues не заводить, доделать журнал. Владелец подтвердил и записал это в #63.
Пауза принята. На момент паузы висело одно незакрытое измерение (И15) — доснял

`amount_minor`) описан в журнале и **не заведён** — ждёт снятия паузы.

ожидание нельзя. Сказал ему об этом прямо.
