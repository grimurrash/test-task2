3. **`.claude/hooks/guard-git.py`**:
   - новая проверка «по факту»: текущая ветка HEAD в директории из `cwd`

     команде, описывающей этот баг в файле через heredoc — тот же класс
     ложной тревоги дважды поймал и эту сессию вживую, см. ниже);

     разделителя) — тот же приём, что уже в `guard-protected-files` и
     `scan-untrusted` (issue #6): команда должна стоять в позиции запуска,
     не быть упомянутой в тексте.

   через полные пути веток не покрыта.

## Решения

| Решение | Обоснование |
|---|---|
| Проверка HEAD дополняет проверку по имени ветки, не заменяет | прямое требование issue #20: push не с HEAD, но в защищённую ветку по явному имени — ловится только текстовой проверкой |
| `cwd` события хука, а не переменная окружения проекта | эмпирически подтверждено: у параллельной сессии (контракт, своя рабочая копия) `cwd` в реальном событии хука отличался от корня репозитория; переменная окружения фиксирована на весь сеанс и не различает воркеров |
| Сбой проверки по факту не блокирует push | альтернатива — блокировать все push при любой ошибке — создала бы гораздо больше ложных тревог, чем закрывает находок; текстовая проверка остаётся барьером на явно названные защищённые ветки независимо от исхода этой проверки |
| Heredoc вырезается для всех проверок файла, не точечно для push | тот же класс ложной тревоги угрожает любому правилу `guard-git`, не только push-проверке; точечное исключение для одной проверки оставило бы дыру для остальных |
| Регрессии — на настоящих git-репозиториях, не на текстовых полях | без реального репозитория с управляемым HEAD проверка проверяла бы только заглушку; мокать вызов git означало бы проверять мок, а не поведение |

## Живая проверка отладкой (не для мерджа)

Перед реализацией временно вставлен вывод сырых данных события хука во
временный файл, вызвана безобидная git-команда в этой же сессии, вывод
прочитан, отладка убрана до правки по существу. Побочный эффект: временный
файл в общесистемной папке тут же перезаписала другая параллельная сессия —
подтвердило, что у ролей действительно разный `cwd`, но заодно и урок на
будущее: свои отладочные файлы — в scratchpad сессии, не в общую временную
папку напрямую.

Отдельно, дважды за эту сессию собственный тестовый скрипт для проверки хука
и черновик этого журнала сами попадали под ещё не починенный хук — длинные
инлайн-команды с описанием бага текстом воспроизводили ту самую ложную
тревогу, которую чинили. Оба раза обойдено переносом текста в файл через
файловый инструмент вместо составной команды в терминале — рабочий обход,
не имеющий отношения к качеству самой правки.

## Решения

| Решение | Обоснование |
|---|---|
| Чинить, несмотря на то что живая эксплуатация не подтвердилась | тестовый харнесс реально ломается этим способом (тот же механизм, что и воспроизведение в задаче), а полагаться на нынешнее поведение обвязки как на гарантию — держать границу на допущении. И issue, и сэр решение не отменяли |
| `gate-quality` не переведён на общий `repo_root()` | ему нужен каталог, где **реально** шла работа — там же спрашивается `git status` и считаются mtime исходников. Общий корень основной копии проверял бы чужое рабочее дерево, если сессия работает в worktree, — гейт перестал бы видеть ровно то, ради чего существует. Расхождение с буквальным списком задачи, названо в приёмке заранее, не молча |
| `guard-secrets.py` и `scan-untrusted.py` не тронуты | оба проверены чтением: секреты определяются абсолютными шаблонами без понятия «корень», `scan-untrusted` использует `project_dir()` только для пути к логу, не для решения о границе. Не тот класс дефекта |
| Регрессии — с настоящим `git worktree add`, а не с двумя независимыми временными репозиториями | issue #20 показал, что синтетика мимо реальной структуры может не поймать баг вовсе (см. «Что сделано», п. 7) — здесь та же осторожность оправдалась ещё раз |
| Тест на самоссылающийся путь, а не на «соседний» | ранняя версия с другим именем worktree проходила даже на сломанном коде — регрессия обязана падать без фикса, иначе это не регрессия, а декорация |
| Синтетические репозитории — не в системном `/tmp` | найдено первым прогоном CI (см. ниже): у `guard-scope` есть отдельное, намеренное исключение — `/tmp`/`/private/tmp` пропускают границу мимо проверки вовсе. На Linux `tempfile.mkdtemp()` без `dir=` кладёт файлы буквально в `/tmp`, и тест был зелёным независимо от того, работает ли сама проверка. На macOS `mkdtemp()` уходит в `/var/folders/…`, поэтому локально это не всплывало — расхождение CI/локально было расхождением тестового окружения, не фикса |

## CI разошёлся с локальным прогоном — отдельный разбор

Первый пуш PR #30 дал 4 провала в CI при полностью зелёном локальном прогоне —
все четыре ровно там, где регрессия должна была ловить баг. Не стал гадать
по логам: добавил временную диагностику (`_REPO_ROOT_DEBUG`, печать `base`,
`rc`, `stdout` вызова git в `repo_root()`) и печать `stderr` при провале
в самих тестах, прогнал через настоящий CI (быстрее и надёжнее локальных
попыток воспроизвести окружение GitHub Actions наугад).

Диагностика показала: `repo_root()` считает корень **верно** —
`/tmp/guard-scope-root-XXXXXX` совпадает с git `--git-common-dir`. Проблема
не в фиксе, а в том, что `resolved` (для `../outside.txt`) тоже попадал под
`/tmp` — а `guard-scope.inside()` считает `/tmp` и `/private/tmp` **всегда**
безопасными, независимо от корня (тот же код, что даёт `allow` кейсу
«временная папка разрешена» в основном наборе). Тест сам себя обесценивал
на Linux, там, где `mkdtemp()` без аргумента `dir=` буквально создаёт папки
в `/tmp`. Закрыто: синтетические репозитории переехали в `/var/tmp`
(есть на обеих платформах, не входит в исключение). Отладка убрана после
диагностики — оставлять постоянный debug-вывод в общем `_hooklib.py` не стал,
это разовая диагностика, а не постоянно нужная возможность.

Урок для протокола: ложноположительный локальный прогон — тот же по сути
риск, что и ложная тревога хука, только в другую сторону. Тест, зелёный
по случайности окружения, не отличить от теста, зелёного по правильной
работе кода, — без прогона там, где условия реально другие.

## Противоречие в задании — названо, не обойдено молча

Задание требует пропуск **только по маркеру в самом файле** и одновременно
ставит критерием приёмки «CI на PR #40 позеленел **без единой правки
в `backend/`**», запрещая править чужой тест. Эти три условия несовместимы:
чтобы `backend/test/validation.test.ts` перестал валить сканер, строка
с маркером обязана появиться именно в нём.

Проверено фактом, а не рассуждением: файла нет в `main`, он живёт в ветке
`feature/backend-api`; прогон сканера по его содержимому даёт одну находку —
русскоязычный образец в массиве тестовых значений `description`. Образец
лежит по делу, убирать нельзя, согласен.

Предложены два варианта, решение — за проджектом: (А) бэкенд-сессия сама
добавляет одну строку-комментарий в шапку своего файла; (Б) её добавляю я
в этой же ветке, но тогда «без правок в `backend/`» не выполняется буквально.
Работа над механизмом не блокировалась — он нужен в любом варианте.

## Решения

| Решение | Обоснование |
|---|---|
| Маркер действует только в шапке (первые 2 КБ) | иначе строка, оказавшаяся в глубине внешнего текста, отключала бы проверку файла — а сканер существует ровно ради внешнего текста. Заодно выполняет требование задания «виден человеку, а не спрятан» |
| Маркер — обычная подстрока, не регулярка и не формат | работает в комментарии любого языка (`#`, `//`, `<!-- -->`) без отдельного парсера на каждый |
| Пропуск по-прежнему пофайловый | «маркер в каталоге» превратил бы одну строку в отключение проверки для всего дерева рядом |
| Клапан `guard-allow.txt` на маркер не распространяется | прямая граница из задания: это разные механизмы, смешивать не надо |

### Дополнение к #42: проджект переоценил задачу по ходу работы

Уже после того, как первый вариант фикса был запушен (PR #46), Ранис перечитал
задачу, поставил метку `bug` и назвал ещё два дефекта. Оба приняты, оба закрыты
в той же ветке — переоценка по существу, не по формулировке, спорить не с чем.

1. **Обход, а не шум.** `SELF_FILES` сравнивался с basename: любой файл
   с именем `test_hooks.py` или `scan_untrusted.py` — где угодно в дереве,
   включая пришедший извне, — молча выпадал из проверки. Маркер в содержимом
   закрывает это **по построению**, но заявлять «закрыто по построению»
   без прогона нельзя: проверено отдельным пробником на настоящем дереве
   (`/var/tmp/.../downloaded-repo/scripts/test_hooks.py` с образцом, без
   маркера → находка, `rc=1`), затем закреплено регрессией.
2. **Вторая папка копий.** Платформа заводит `.claude/worktrees/` помимо нашей
   `.worktrees/`; в `SKIP_DIRS` её не было, сканер ходил внутрь и проверял
   полный дубль. Добавлены обе.
3. **Найдено при этом самим, третьим:** `.claude/logs` стоял в `SKIP_DIRS`
   и **не работал никогда** — там сравнивается имя каталога (`logs`), а не
   путь. Тот же класс ошибки, что и пропуск файлов по basename. Введён
   отдельный `SKIP_REL_PATHS` — сравнение по пути от корня сканирования.

Регрессий в разделе стало девять: четыре на маркер, одна на «пропуск
не расползается на каталог», одна на обход по имени, три на непосещаемые
каталоги.

`docs/HOOKS.md` дополнен разменом, который просил назвать проджект: копия
пропускается потому, что сканируется оригинал; файл, которого в оригинале
нет, проверку не пройдёт. Для CI (чистый клон без копий) это безопасно,
для локального прогона — известная граница, а не гарантия.
