## Порядок работы и почему такой

Задание требует читать контракт раньше кода. Я усилил это правило до порядка,
в котором ошибиться сложнее:

1. контракт `openapi/openapi.yaml` из `main` и `docs/product/PRD.md` — целиком, до всего;
2. **сначала ломаю живой API запросами**, не открывая `backend/`;
3. потом читаю код — уже имея свой список наблюдений;
4. потом читаю тесты;
5. и только в конце — проверяю тесты мутациями.

Смысл шага 2 перед шагом 3: если сначала прочитать код, проверять начинаешь
не контракт, а собственный пересказ реализации. Половина находок этой сессии
(500 на кривом пути, обрыв на большом теле) получена именно вслепую.

## Решение 1. Границы проверки

Не чиню и не трогаю `backend/` — задание это запрещает прямо. Мутации, без которых
тесты не проверить, гоню **в копии вне репозитория**:
`git archive origin/feature/backend-api | tar -x -C <scratchpad>` плюс контракт
из `main`. Ветка автора и рабочее дерево остаются нетронутыми: `git status` чист
всё время работы.

## Решение 2. Что считать находкой

Расхождение поведения с контрактом — находка. Несогласие с самим контрактом —
вопрос проджекту, а не автору (#32 закрыта). Замечания про стиль не пишу вовсе:
на них есть линтер, и десять придирок к именованию — это способ выдать пустой
результат за работу.

Отдельно решил: **ноль находок — законный итог**. Задание ждёт «четвёртый
неразличающий тест», и это формулировка, которая подталкивает найти его любой
ценой. Подгонять не стал; см. решение 5, где ответ оказался обратным ожиданию
проджекта.

## Ход проверки

### Шаг 1. Контракт

Прочитан целиком, включая поправки A–F из #32. Выписал места, где контракт
допускает толкование и где, значит, вероятны расхождения: порядок проверок,
определение «того же тела», пересечение `idempotency_key_reuse` и
`request_in_progress`, CORS на ошибках, граница `5xx`.

Заодно замечено расхождение **PRD против контракта**: F8 и F9 обещают 400
`invalid_amount` и `invalid_currency`, которых в перечне `ErrorCode` нет вовсе —
контракт свёл валидацию в 422 `validation_failed`. Проверял по контракту,
расхождение вынес проджекту как вопрос о PRD, не автору.

### Шаг 2. Живой API вслепую

API в контейнере `psp-api` на `http://localhost:8080`. Прогнал ~60 запросов:
базовая идемпотентность, порядок проверок, все границы из пункта 4 задания,
CORS и preflight, скоуп мерчанта, жизненный цикл, тестовые суммы, path-трюки,
размеры тела, гонки на 20 и на 10×2 запросах.

Здесь получены находки 1 и 3 — обе на входах, которых нет в тестах автора.

### Шаг 3. Код

Читал на устройство, а не на стиль. Хранилище оказалось аккуратнее, чем я ожидал:
критическая секция `reserve` действительно без `await`, тай-брейк сортировки по
`seq` есть (моё подозрение про совпадающие `created_at` снялось), освобождение
брони при сорвавшемся создании написано. Находка 2 пришла из чтения
`validateCreateBody`: карта нарушений собирается в объект с прототипом.

### Шаг 4. Тесты

Прочитаны как код. Обвязка сильная: `assertMatchesContract` вызывается на каждом
ответе, забыть проверку контракта в отдельном тесте нельзя. Заметил, что
`raw()` этой проверки не делает — там и живут непокрытые ответы.

### Шаг 5. Мутации

17 мутаций в копии, каждая ломает один инвариант. Поймано 14, три — нет
(см. отчёт). Плюс отдельный прогон по методике проджекта из поправки к #47.

## Решение 3. Находки, которые я оставил дефектами

Три расхождения с контрактом, все воспроизведены дважды: на живом API
в контейнере и на чистой сборке кода ветки без контейнера.

1. **Кривая процентная последовательность в пути → 500.**
   `GET /v1/payments/%zz` даёт `internal_error` вместо 404 `payment_not_found`,
   и обходит порядок проверок: без `X-Merchant-Id` тоже 500, а не 400.
   Причина — `decodeURIComponent` в `matchRoute` без защиты, `URIError`
   в логе сервера.
2. **`__proto__` в теле обходит `additionalProperties: false`.**
   201 вместо 422. Причина механическая: `errors['__proto__'] = ...` уходит
   в сеттер прототипа и собственного свойства не создаёт, поэтому
   `Object.keys(errors).length` остаётся нулём.
3. **Тело больше 1 МБ — обрыв соединения вместо ответа.**
   Код формирует корректный 400 `malformed_request`, но `req.destroy()`
   выполняется раньше, чем ответ уходит. Для песочницы это сетевая ошибка —
   ровно то, ради предотвращения чего контракт требует CORS на всех ответах.

## Решение 4. Что я находкой не считаю

- Коды `not_found`, `method_not_allowed`, `internal_error` вне перечня `ErrorCode` —
  автор объявил их в `OffContractErrorCode` и оговорил, что контракт этих
  ситуаций не описывает. Согласен, претензию снял. Исключение — пункт 1 выше:
  там 500 приходит на **описанном** контрактом маршруте.
- `description: null` → 422. Контракт в запросе объявляет поле `type: string`
  без `null`, в отличие от ответа. Реализация читает строго; асимметрия
  контракта, а не дефект кода.
- Одиночный процесс как условие корректности — названо в PR и в комментарии
  кода честно и заранее.

## Решение 5. Спор о тесте 248 — прогон, а не мнение

Проджект прислал поправку к заданию: тест «десять одновременных отправок»
(`idempotency.test.ts:248`) — предмет разногласия. Автор считает его
неразличающим по построению, проджект по чтению усомнился; оба сознательно
не гнали прогон, чтобы не подсунуть готовый ответ.

Мутация — та, что указана в поправке: `#keys.set` убран из `reserve()`
и перенесён в `commit()`, то есть классическое «проверил — записал» со щелью.
Прогонов **25** (10 + 15), поимённо по трём тестам гонки.

**Результат: тест 248 красный 0 раз из 25.** Тесты 215 и 269 (оба с барьером) —
красные 25 из 25.

Это не «мигающий», а устойчиво неразличающий: третий, худший исход из таблицы
проджекта не подтвердился. Механизм замерил отдельно — пик одновременных
фиксаций в этом сценарии равен единице, запросы не пересекаются вовсе.
Проверка чувствительности: если уступку в фиксации расширить с `setImmediate`
до `setTimeout(5)`, тот же сценарий на наивной схеме даёт 10 создателей.
Значит исход теста задаёт длительность уступки, а не бронь ключа.

**Спор решён в пользу автора, не проджекта.** Записываю это прямо: проверка
затевалась ради независимого ответа, и ответ оказался не тем, которого ждала
сторона, формулировавшая задание. Рекомендация — та, которую сам проджект
назначил на этот исход: тест не удалять, а назвать своим именем.

## Решение 6. Вердикт

**Принять с замечаниями.** Ядро задачи — идемпотентность, гонка, TTL, скоуп
мерчанта, валидация, жизненный цикл — соответствует контракту и защищено
тестами, которые действительно ловят поломку: 14 мутаций из 17 пойманы,
и обе барьерные проверки гонки краснеют стабильно.

Три расхождения с контрактом лежат на краях входа и чинятся точечно, без
пересмотра устройства. Оговорка, которую обязан сказать: находка 1 нарушает
критерий A7 на описанном контрактом маршруте. Если A7 принимается строго,
её надо закрыть до слияния; это решение проджекта, не моё.

маркеры инъекции и записал находку в `.claude/logs/untrusted.jsonl`. Это

что правило требует называть такие находки вслух, а не глотать их молча.
