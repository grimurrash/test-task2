# Салават-156 — задача #156

Упавший хук разрешает команду: необработанное исключение даёт код 1,
а барьером служит только код 2.

Копия: `.worktrees/hook-failure-denies`. Ветка: `fix/hook-failure-denies`.
Координатор: сессия «Карина [2a8ba0]». Приём подтверждён первым сообщением.

## Задание дословно (существенное из тикета)

> Каждый хук на `PreToolUse` заканчивает работу решением, а не трассировкой:
> необработанное исключение перехватывается на верхнем уровне и превращается
> в отказ с названной причиной («разбор не завершён»), а не в код 1.
> Форма — на усмотрение исполнителя. Требование одно: ни один путь выполнения
> не заканчивается кодом 1.

Приёмка по тикету:

1. искусственно сломанный хук даёт **deny с причиной**, проверка на всех
   хуках `PreToolUse`, а не на одном;
2. парная половина: обычная безобидная команда по-прежнему проходит;
3. в `guard.jsonl` запись о сбое разбора, отличимая от обычного отказа.

Отдельно от координатора: задача про класс, а не про одну форму; соседние
сессии заняты `scan-untrusted.py` (#162) и `scripts/scan_untrusted.py` (#163) —
эти два файла не трогаю.

## Что понято при разборе

**Механика бага.** Все пять хуков `PreToolUse` заканчиваются вызовом `main()`
на верхнем уровне модуля. Необработанное исключение печатает трассировку
и завершает процесс кодом 1. Барьером Claude Code считает код 2 либо код 0
с JSON `permissionDecision: deny`; код 1 — «неблокирующая ошибка», команда
исполняется. Проверка, не дошедшая до решения, оказывается разрешением.

**Список хуков на `PreToolUse`** (из `settings.json`): guard-secrets, guard-git,
guard-roles, guard-scope, guard-protected-files. Ровно пять. `lint-claude-md`
хуком не является — это CLI, который зовёт `session-start.sh`; `mark-verify`
и `scan-untrusted` висят на `PostToolUse`, `gate-quality` — на `Stop`.

**Живой экземпляр из тикета не воспроизводится.** Команда с тысячей вложенных
heredoc (и ещё четыре формы того же класса: вложенные `$(…)`, тысяча тел
heredoc, 200 КБ в одном токене, тысяча скобок внутри `python3 -c`) прогнаны
через все пять хуков — код 0, трассировок нет. Рекурсию закрыл #103, как
и было сказано в тикете. Значит проверять надо не форму, а класс: тест обязан
ломать хук искусственно, иначе он проверяет чужую починку.

Проверено:

    5 форм × 5 хуков → rc=0 на всех 25 запусках

## Решения

**Механизм — `sys.excepthook`, а не `try` вокруг `main()`.** `try` вокруг
вызова `main()` не покрывает падение на уровне модуля: импорт `_paths`,
компиляция регулярок, вычисление `HOME` из окружения. Это тот же класс —
код не дошёл до решения, — и он остался бы открытым. Обработчик ставится
одной строкой сразу после импорта библиотеки хуков, то есть раньше всего
остального кода модуля.

Поведение проверено экспериментом до правки кода (`python3` в песочнице):

| случай | результат |
|---|---|
| исключение на уровне модуля (сломанный импорт) | обработчик вызван, rc=0, решение напечатано |
| `RecursionError` из `main()` | обработчик вызван, rc=0, решение напечатано |
| обычный `sys.exit(0)` | обработчик не вызван — штатные решения не затронуты |
| обработчик сам бросил исключение | «Error in sys.excepthook», **rc=1** |
| stdout закрыт, решение напечатать нельзя | stderr + `os._exit(2)` — барьер остаётся |

Отсюда два требования к самому обработчику: он не имеет права бросить
исключение (ловится `BaseException`, каждый шаг в своём `try`) и выходит
через `os._exit`, а не `sys.exit` — `SystemExit` внутри обработчика CPython
проглатывает молча, без вывода.

**Граница задачи названа явно** (см. план, раздел «Чего эта задача не делает»):
`gate-quality` (Stop) и хуки `PostToolUse` сюда не входят, и не по недосмотру.
