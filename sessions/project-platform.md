## Решение 1: приёмку #43 вести без локального прогона набора

**Обстановка.** В `.claude/state/unlock.json` на 16:35 лежали три действующих
пропуска сэра (`protected-files`, `git-worktree`, `git-branch`). Правило проекта
требует подтверждать приёмку выводом команды; очевидная команда — прогон набора
проверок. Но открытая #54 говорит ровно то, что этот прогон делает с чужим
состоянием.

**Решение.** Набор локально не гонять. Зачесть изолированный прогон в CI
(он зелёный) и проверять фикс точечно, сравнивая поведение `_paths` из `main`
и из ветки на одном входе.

**Почему так.** Прогон стоил бы сэру трёх выданных действий, а соседним ролям —
отказов посреди прогона. Цена ошибки в обратную сторону — недопроверенная
приёмка — снималась точечными пробами, и они оказались сильнее прогона:
CI был зелёным, а дыры нашлись.

**Побочный вывод, годный для отчёта.** «Сделано подтверждается выводом команды»
и «прогон вредит соседям» сейчас противоречат друг другу. Пока #54 открыта,
принимающий выбирает между двумя плохими вариантами. Это не философия,
а конкретный дефект с номером.

## Решение 2: #43 / PR #53 — на доработку

Проверка — сравнение одного и того же входа на двух версиях общего модуля,
пути взяты внутри разрешённой временной папки нарочно: показывается не запрет,
а то, что проверять стало нечего.

```
main  'docker ps && rm -rf /tmp/probe-target'              -> ['/tmp/probe-target']
main  'docker compose up -d && rm -rf /tmp/probe-target'   -> ['/tmp/probe-target']
main  "bash <<'SH'\nrm -rf /tmp/probe-target\nSH"          -> ['/tmp/probe-target']
PR53  'docker ps && rm -rf /tmp/probe-target'              -> []
PR53  'docker compose up -d && rm -rf /tmp/probe-target'   -> []
PR53  "bash <<'SH'\nrm -rf /tmp/probe-target\nSH"          -> []
```

**Дыра 1.** Docker-команда в любой стадии конвейера снимает проверку путей
со всей команды. Отсюда `docker compose up -d && rm -rf <наружу>` мимо границы
репозитория — форма, которой поток обвязки занят каждый день.

**Дыра 2.** Тело heredoc вырезается независимо от получателя. Для `cat > file`
это данные, для `bash <<`, `sh <<`, `python3 - <<` — исполняемый код. И вырезание
живёт в `normalize()`, который импортирует ещё и `guard-secrets`: запрет,
заведённый против «обхода через `python -c`», обходится сменой формы на heredoc.
У `guard-git` та же дыра была и до этой правки — проверено на обеих версиях;
исполнитель её не создавал, но перенос разбора в общий модуль делает её общей
на четыре хука.

**Что зачтено:** отказ чинить по описанию задачи и переход к настоящим отказам
из журнала; парные проверки на каждое сужение; публичный разбор собственной
дыры в первой версии фикса.

**Заметка процессу.** Зелёный CI не доказал ничего: тесты к фиксу пишет автор
фикса. Это прямое подтверждение правила «приёмку делает не автор» — в отчёт
по #18 идёт фактом, а не лозунгом.

## Решение 3: формулировку #54 ужесточить до «перенаправление, а не восстановление»

Задача была написана как «тесты не изолируют состояние». По коду набора это
неточно и уводит к дешёвой неправильной починке: изоляция там есть, боевой
`unlock.json` **удаляется** на время прогона и возвращается **снимком**,
снятым до старта. Следствий три: пока идёт чужой прогон, действующего пропуска
нет ни у кого; пропуск, выданный во время прогона, теряется при восстановлении;
журнал не изолирован вовсе — у него берётся только размер.

Отсюда требование: свой каталог состояния и свой журнал, боевые файлы за прогон
не открываются вовсе. «Восстанавливать аккуратнее» или «сливать записи» не
принимается — гонка остаётся, сужается только окно.

## Сессия 1, продолжение · собственная декоративная проверка

Проверяя доработку #43, прогнал контрольные пробы на защиту файлов правил:
«правка файла хука документом» и «правка через `sed`» — обе получили **allow**
у обеих версий хука. Секунду выглядело как дыра размером с ворота.

Проверил состояние прежде, чем писать вердикт: в этот момент была **открыта зона
`protected-files`** — пропуск, выданный сэром исполнителю под работу по #54.
То есть проба измеряла не поведение хука, а действующее разрешение.

**Это ровно тот класс, который мы весь день ищем в чужих тестах:** проверка,
чей результат держится **средой**, а не проверяемым кодом. У бэкенда свойство
держал тайминг, у фронта — соседняя функция, у меня — открытая зона. Разница
только в том, что мой случай поймался до того, как я объявил результат.

Практическое следствие для приёмок в этом потоке: **любая проба защиты сначала
сверяется с состоянием пропусков**, иначе она декоративна. Пробы перезапускаются
после истечения зоны.

Открытым остаётся девятый случай задачи — чтение собственного состояния внутри
встроенного кода по-прежнему отказ. Поймал на себе дважды. Проверить из своей
сессии не могу: проба обязана упомянуть тот же путь и блокируется раньше, чем
доедет. Пара — за исполнителем.

## Три собственных промаха на приёмке, все одного класса

Записываю подробно, потому что это лучший материал дня для отчёта: **проверяющий
сам трижды получил результат, державшийся не тем, о чём он говорил.**

1. **Проба при открытой зоне.** Контрольные пробы на защиту правил дали
   «разрешено» там, где ждался отказ. Секунду выглядело дырой размером с ворота.
   На деле измерялся живой пропуск, а не хук.
2. **Чужая копия уехала под руками.** Первые замеры шли через рабочую копию
   исполнителя; посреди приёмки он переключил её на ветку compose, и две пробы
   сравнили `main` сам с собой, показав «ноль изменений». Едва не принял
   за результат. Вывод: **копию под приёмку заводит принимающий.**
3. **Журнал хранит команду обрезанной.** Повтор настоящих отказов из журнала —
   метод хороший, но для длинных команд отвечает неверно: в записи начало команды,
   а не вся она. Замер «ноль из 54 изменилось» на этом сломался, вывод снят.

Ни один из трёх не был бы заметен по виду результата: все три выглядели как
нормальные измерения.

## Уточнение к #54, полученное измерением, а не рассуждением

Прогон набора **из рабочей копии** боевое состояние не трогает: sha256
боевого `unlock.json` и размер боевого журнала до и после прогона совпали
побайтово. Причина — корень набора вычисляется от расположения самого файла.

Отсюда две вещи. Первая: пока #54 не закрыта, ролям следует гонять набор из своей
копии — тогда и гейт качества доволен, и чужие пропуска целы. Вторая: формулировка
#54 сужается ещё раз — дефект не в наборе вообще, а в прогоне **из главной копии**.

## Решение 10: R4 — вариант с отдельным тестовым сервисом, формулировка PRD — к продукту

Исполнитель нашёл противоречие: R3 запрещает держать в рантайме тесты
и `devDependencies`, а R4 и критерий A11 требуют запускать тесты дословной командой
на сервисе `backend`, который и есть рантайм. **Команда из R4 на образе из R3
невыполнима в принципе.** Пролежало это в PRD весь проект и всплыло на предпоследней
задаче — там, где два требования впервые встретились в одном файле.

Решение: отдельный сервис для тестов под профилем, чтобы не поднимался третьим
контейнером. Формулировку R4 и A11 правит **продукт** — PRD заморожен, и это
не моя зона; расхождение отправлено с готовой редакцией. Работу это не держит:
сервис нужен один и тот же при любом исходе.

Отклонён вариант «назвать тестовый сервис `backend`, а рабочий `api`»: команда
из PRD заработала бы дословно ценой того, что главный сервис проекта называется
не своим именем. Менять реальность под текст — худший вид следования требованиям.

## Счёт ложных отказов, полученных лично за сессию приёмки

Четыре: путь внутри контейнера в тексте акта; чтение `unlock.json` внутри
встроенного кода — дважды; путеподобная строка в данных сравнения. Все —
«строка упомянута, а не использована». Ни один не обойдён: три раза
переформулировал, один раз отказался от замера.
