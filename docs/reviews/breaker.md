### D1 · Дублирующийся `Idempotency-Key` ломает идемпотентность — два платежа на один ключ

**Важность:** высокая. Это ровно тот отказ, ради которого существует сервис.

Node склеивает повторившийся заголовок в одну строку через `", "`. Приложение
получает `"K, K"` и считает это **другим ключом**. Клиент, у которого прокси или
retry-обвязка добавила заголовок второй раз, а затем повторил запрос корректно,
получает **два списания**.

Воспроизведение (мерчант и ключ произвольные, лишь бы новые):

```
$ curl -s -w '  <- %{http_code}\n' -X POST http://localhost:8095/v1/payments \
    -H 'Content-Type: application/json' \
    -H 'Idempotency-Key: key-1470' -H 'Idempotency-Key: key-1470' \
    -H 'X-Merchant-Id: dupdemo-11522' \
    -d '{"amount_minor":125000,"currency":"RUB","order_id":"o-dup"}'
{"id":"pay_Se4aXaIJ0IHp"  <- 201

$ curl -s -w '  <- %{http_code}\n' -X POST http://localhost:8095/v1/payments \
    -H 'Content-Type: application/json' \
    -H 'Idempotency-Key: key-1470' \
    -H 'X-Merchant-Id: dupdemo-11522' \
    -d '{"amount_minor":125000,"currency":"RUB","order_id":"o-dup"}'
{"id":"pay_BbsGKi732bwk"  <- 201

$ curl -s http://localhost:8095/v1/payments -H 'X-Merchant-Id: dupdemo-11522'
платежей: 2
  pay_BbsGKi732bwk o-dup
  pay_Se4aXaIJ0IHp o-dup
```

Ожидание по контракту: `Idempotency-Key` — «непустая строка от 1 до 255 символов»;
второй запрос обязан вернуть **200 и тот же ресурс**. Нарушены F1, F2 и смысл F4.

Где смотреть: `backend/src/domain/validation.ts`, функция `headerValue` —
`Array.isArray(raw) ? raw.join(', ') : raw`. Ветка с массивом в бою недостижима
(Node отдаёт уже склеенную строку, проверено — см. `.qa-tmp/header-shape.mjs`),
а склейку приложение не замечает вовсе. Решение принимает бэкенд; вариантов
как минимум два — отвергать дубль (400) или брать первое значение.

### D2 · Коды `method_not_allowed` и `not_found` не описаны контрактом

**Важность:** средняя (A7 — «поведение API соответствует `openapi.yaml`»).

```
405 | DELETE на коллекцию      | method_not_allowed
405 | PUT на платёж            | method_not_allowed
405 | GET на /cancel           | method_not_allowed
404 | POST на несуществующий путь | not_found
```

`components/schemas/ErrorCode` перечисляет ровно десять кодов; этих двух там нет.
Статус 405 не описан ни у одного пути. Либо контракт достраивается, либо сервис
отвечает описанными кодами — решает не QA.

### D3 · `U+202E` в `description` переворачивает отображаемый текст в песочнице

**Важность:** низкая. Скрипты не исполняются (A10 держится), но отображаемая строка
перестаёт совпадать с хранимой: `Ünïcödé ✅ 😀 中文 عربى ‮текст-справа-налево`
выводится как `… -тскет овелан-аварпс`. Управляющий символ действует и на соседний
текст внутри блока описания. Контракт говорит «хранится и отдаётся как есть» —
это про хранение; U6 говорит «выводится как текст» — формально выполнено.
Называю, потому что описание задаёт мерчант, а читает человек.

## Находки по тестам, а не по продукту

### H1 · Набор бэкенда не различает нарушение F11 «хранится как есть»

Мутация **M17**: `description` сохраняется обрезанным по краям
(`.trim()` в `validateCreateBody`). Прогон: **187 зелёных, 0 красных**.

Мутация доехала — проверено запуском мутантной сборки рядом с продуктовой:

```
--- эталон (продуктовый код, :8095) ---
description = "  текст с краевыми пробелами  "
--- мутант M17 (:8096) ---
description = "текст с краевыми пробелами"
```

То есть нарушение наблюдаемо через публичный интерфейс и при этом не красит
ни одного теста. Дыра в наборе, а не дефект продукта.

### H2 · `request_in_progress` в боевой конфигурации недостижим

Контракт заявляет 409 `request_in_progress` как один из двух законных исходов гонки,
песочница пишет об этом пользователю. За 40 раундов сокетной гонки (итерации 3–4)
код не встретился ни разу. Причина в коде: `app.ts:153` подставляет
`commit: deps.commit ?? (() => undefined)`, поэтому `await` в `PaymentService.create`
уступает только микрозадаче, а другой HTTP-запрос — макрозадача. Окно существует
лишь когда `commit` подменён асинхронным барьером, то есть **только в тесте**.

Тест `backend/test/idempotency.test.ts:283` не декоративен — он различает поломку
самой ветки. Но проверяет он конфигурацию, которой в бою нет. Это не то же самое,
что «свойство держится кодом».

Побочно: ветка `Array.isArray(raw)` в `headerValue` — мёртвый код (см. D1).
