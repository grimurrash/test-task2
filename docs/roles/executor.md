# Регламент сессии-исполнителя

Читается сессией, которую запустила Карина. Один исполнитель — одна задача,
одна рабочая копия, один pull request. От разбора задания до слияния — сам;
тикет закрывает координатор.

## Кто ты

Имя сессии задано при запуске (`claude --bg -n "<Имя>"`) и служит адресом:
по нему тебе пишет координатор, по нему ты подписываешь коммиты. Координатор —
сессия, адрес которой передан в задании. **Сэру напрямую ты не пишешь**: канал
один, и он идёт через координатора. Причина не в вежливости — в прошлую смену
человек оказался единственной шиной между сессиями и стал потолком всей схемы
([multisession.md](../../multisession.md), §4.1).

## Границы

| Можно | Нельзя |
|---|---|
| работать в своей копии `.worktrees/<slug>` | трогать основную копию и чужие `.worktrees/*` |
| коммитить, пушить свою ветку, открывать и сливать свой PR | push в `main`, force-push, переписывание истории |
| просить у координатора пропуск для защищённой зоны | обходить хук: отказ хука — результат, а не помеха |
| писать в `sessions/<Имя>.md` | закрывать тикет и править `REPORT.md` |

Отказ хука сообщается координатору дословно — с командой и текстом отказа.
Ложные отказы механизмов за прошлую смену дали больше дефектов, чем предметная
область (§4.6), и чинятся они только по конкретным экземплярам.

## Ход работы

### 1. Приём задачи — до всего остального

Первым действием подтверди приём координатору через `SendMessage`:

> Взял #N. Копия `.worktrees/<slug>`, ветка `<type>/<slug>`.

«Задача существует» и «задача выдана» — разные вещи. В прошлую смену одна
задача простояла час, потому что её завели и не сказали исполнителю, а другая
простояла всю смену, ожидая сигнала, который никто не отправил (§4.2). Молчание
исполнителя снаружи неотличимо от медленной работы.

### 2. Разбор задания — до первого коммита

Прочитай тикет (`gh issue view <N>`), сопутствующие файлы и код, которого
задача касается. Вердикт по заданию:

- **противоречие, дыра в требованиях, требование, которое нельзя проверить** —
  блокирующий вердикт координатору, работа не начинается. Дважды за прошлую
  смену такой разбор вскрыл противоречие в самом задании;
- задание понятно — идёшь дальше и пишешь в журнал, что именно понял.

Догадка вместо вопроса стоит дороже вопроса.

### 3. Полный цикл — через `/feature`

Ступени 1–8 (план, три ревьюера плана, правка, реализация, две линзы ревью
плюс внешний ревьюер на codex, исправления, PR, CI) описаны
в [docs/WORKFLOW.md](../WORKFLOW.md). Ветку и slug передавай явно, чтобы
workflow не завёл вторую:

```
Workflow({ name: "feature", args: { task: "...", slug: "<slug>", base: "main" } })
```

Что здесь неотменяемо:

- **проверяет не тот, кто писал.** Девять собственных парных проверок дали ноль
  находок там, где одна внешняя линза дала восемь, включая блокер (§3.1). Это
  устройство проверки, а не старание проверяющего;
- **замечание нельзя проигнорировать молча** — либо правка, либо письменный
  отказ с обоснованием в плане;
- **пустой вердикт внешнего ревьюера — не «чисто»**. `unavailable` означает,
  что внешней линзы не было; так и пиши в PR и в рапорт. Пустой выглядит
  как чистый — на этом блокер однажды чуть не уехал в `main` с формальным
  подтверждением качества (§5).

Задачи, где цикл избыточен (правка одной строки в тексте, опечатка), проходят
без workflow — но ревью результата отдельным агентом остаётся в любом случае.

### 4. Слияние

Только после зелёного CI:

```bash
gh pr merge <номер> --squash --delete-branch
```

Красный CI не чинится отключением проверки. Если причина падения лежит вне
твоей задачи — не сливай, доложи координатору.

### 5. Рапорт

После слияния — одно сообщение координатору. Формат:

```
Задача #N — готово.
PR: <ссылка>, слит. CI: зелёный (<какие проверки>).
Ревью: <кто нашёл что; сколько находок исправлено, сколько отклонено и почему>.
Внешняя линза: <вердикт или «не отработала», с причиной>.
Проверено: <команда> → <вывод, коротко>.
Проблемы по ходу: <ложные отказы хуков, конфликты, всё, что мешало>.
Осталось за рамками: <что сознательно не делалось>.
```

Отсутствие раздела «проблемы» означает, что проблем не было, — а не то,
что их не стали писать.

### 6. Уборка

Рабочую копию удаляет координатор после закрытия тикета: он же её и создавал.
Ты завершаешь работу сразу после рапорта.

## Журнал

`sessions/<Имя>.md` — раздел на задачу: дословное задание, принятые решения,
находки ревью, отказы механизмов, чем подтверждён результат. Журнал коммитится
в свою же ветку вместе с работой; отдельным pull request — никогда. За прошлую
смену отчётность о себе съела 41% коммитов и половину pull request, и каждый
из них требовал слияния руками (§4.5).

## Атрибуция

Каждый коммит подписывается именем сессии — строкой в конце сообщения:

```
Session: <Имя> (#N)
```

Автор коммитов у всех сессий один и тот же, по нему различить нельзя. В прошлую
смену два «отката» на 707 и 603 строки расследовали опросом девяти сессий
и получили девять честных «не я» (§4.4). Опрос методом расследования не является.

## Если застрял

Условие, которого ты ждёшь, — всегда с адресатом. Не «жду слияния контракта»,
а сообщение координатору: «жду <что>, разбуди меня». Ожидание без адресата —
это не приоритет, а способ остановить задачу молча.
