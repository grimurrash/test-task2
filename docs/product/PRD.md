# PRD · Идемпотентный платёжный сервис

**Роль-автор:** продукт · **Сессия:** 1 · **Дата:** 2026-08-24
**Статус:** утверждено сэром · **План:** [docs/plans/psp-idempotency.md](../plans/psp-idempotency.md)

---

## 1. Задача

Повторный запрос на создание платежа не должен создавать второй платёж. Это правило
знают все и почти никто не проверяет: клиент нажал «оплатить» дважды, у мобильного
приложения отвалилась сеть и оно повторило запрос, шлюз переслал вебхук ещё раз —
и в системе оказываются два списания вместо одного.

Делаем сервис, который это правило соблюдает, и **экран, на котором это видно за десять
секунд без чтения логов**.

## 2. Зачем именно это

Идемпотентность — место, где код выглядит правильным и не является таковым. Проверка
«ключ уже есть в хранилище?» с последующей записью выглядит как решение и разваливается
на двух одновременных запросах. Ошибка не воспроизводится вручную и не видна в ревью
глазами — только тестом на гонки. Поэтому тема даёт настоящие дефекты, а не выдуманные.

## 3. Кто пользователь

| Пользователь | Что ему нужно |
|---|---|
| Разработчик-интегратор | понять правила идемпотентности за пять минут и проверить их руками, не написав ни строки кода |
| Проверяющий работу | запустить по инструкции и убедиться, что заявленное поведение действительно есть |

Оба сценария закрываются одним экраном песочницы и одной страницей документации.

## 4. Объём

### Входит

1. **API** — создание платежа с ключом идемпотентности, статус, отмена, список.
2. **Песочница** — один экран, где повтор запроса виден как повтор, а не как новый платёж.
3. **Документация** — страница из `openapi.yaml`, с разделом про идемпотентность
   человеческим языком.

### Не входит

Аутентификация мерчантов сверх заголовка `X-Merchant-Id`, реальные платёжные провайдеры,
вебхуки, личный кабинет, база данных сверх встроенной, деплой на сервер, мобильный клиент,
многовалютная конвертация. Всё это уводит от единственного сценария, который мы
показываем.

**Docker входит в объём** (решение сэра от 2026-08-24): проверяющий разворачивает
всё одной командой, а не собирает окружение по списку предустановок.

## 5. Функциональные требования

### 5.1 Создание платежа

| # | Требование | Проверяется |
|---|---|---|
| F1 | `POST /v1/payments` с заголовком `Idempotency-Key` создаёт платёж в статусе `pending`, отвечает 201 | тест + песочница |
| F2 | Повтор с **тем же ключом и тем же телом** возвращает 200 и **тот же ресурс**, включая `id` и `created_at`. Второй платёж не создаётся | тест + песочница |
| F3 | Тот же ключ с **другим телом** → 409 `idempotency_key_reuse`. Существующий платёж не изменяется | тест + песочница |
| F4 | Две одновременные отправки с одним ключом → ровно один платёж. Проигравший запрос получает либо тот же ресурс, либо 409 `request_in_progress` — но никогда второй `id` | тест на параллельных запросах |
| F5 | Ключ действует ограниченное время (TTL, по умолчанию 24 часа). После истечения тот же ключ создаёт новый платёж | тест с подменой времени |
| F6 | Ключ уникален **в пределах мерчанта**: одинаковый ключ у разных `X-Merchant-Id` — два разных платежа | тест |
| F7 | Запрос без `Idempotency-Key` → 400 `idempotency_key_required` | тест |
| F7c | `Idempotency-Key` — непустая строка **до 255 символов, считая в символах, а не в байтах**. Письменность не навязывается — кириллица, эмодзи и любой другой алфавит допустимы. **Запятая (`,`) и точка (`.`) запрещены** — любое вхождение → 400 `invalid_idempotency_key` | тест: 255 кириллических символов принимаются; запятая и точка в ключе отклоняются |
| F7a | Заголовок `X-Merchant-Id` обязателен. Отсутствует → 400 `merchant_id_required`. Пустой, длиннее 64 символов или вне набора `[A-Za-z0-9._-]` → 400 `invalid_merchant_id` | тест |
| F7b | Ключевой заголовок, присланный **более одного раза**, отклоняется: `Idempotency-Key` → 400 `invalid_idempotency_key`, `X-Merchant-Id` → 400 `invalid_merchant_id`. Считается любая форма повтора — дублирующийся заголовок, несколько значений через запятую, разный регистр имени — **и совпадение значений повтор не отменяет** | тест на **тихий** случай: два одинаковых заголовка не дают двух платежей |

**Одинаковые значения — тоже дубль, и именно этот случай ломается.** Два
заголовка `Idempotency-Key: K` склеиваются в значение `"K, K"` — то есть в **другой
ключ**, тогда как клиент уверен, что послал `K`. Повторная отправка того же
запроса даёт `"K, K"` снова, ключ совпадает сам с собой, и всё выглядит рабочим —
пока между запросами не вклинится вариант без дубля. Требование, прочитанное как
«отклонять дубли с **разными** значениями», оставит дыру ровно там, где она была.

**Почему отклонять, а не выбирать одно из значений.** Ключ идемпотентности —
идентификатор намерения. Два разных значения означают, что клиент сам не знает,
чего просит; молча взять первое или последнее — угадать за него, и угадать
в половине случаев неверно. Цена ошибки здесь ровно та, ради которой существует
проект: второй платёж.

**Почему F7c записано отдельным требованием.** Поведение из него нашёл ломатель
(#75): длина ключа считалась в байтах, и ключ из кириллицы отвергался вдвое
раньше предела. Дефект починили, приёмку прошли, тест на 255 кириллических
символов встал в набор — но **требования в PRD не появилось**. Через несколько
часов правка контракта ввела набор `[A-Za-z0-9._-]`, и он молча отменил принятую
починку: реализация, исполняющая контракт добросовестно, обязана была бы снова
отвергать кириллицу.

Заметил это не проверяющий и не автор правки, а исполнитель, которому предстояло
её реализовать и который помнил, что чинил обратное. То есть спасла память
о собственной работе, а не проверка.

Отсюда правило, которое стоит держать в голове при любой правке: **молчание
о последствии — признак того, что последствие не заметили, а не что его взвесили.**
Если решение отменяет ранее принятое, это пишется прямо: не «что меняем»,
а «что этим отменяем».

**Запрет запятой и точки (2026-08-28, решение сэра, #182).** F7b и F7c какое-то
время требовали противоположного от одного и того же случая: запятая внутри
значения ключа. F7b относил «несколько значений через запятую» к формам повтора
и требовал их отклонять; F7c разрешал любой символ, включая запятую, — и код,
и контракт следовали за F7c. Нашёл расхождение исполнитель на разборе задачи
#180, до первого коммита, а не проверяющий постфактум.

Решение — запретить запятую и точку в значении ключа — снимает расхождение,
не отменяя F7c целиком: письменность по-прежнему не ограничена (кириллица,
эмодзи — 255 символов принимаются, как и раньше), под запретом — ровно два
символа пунктуации. Это не повторяет ошибку контракта из истории выше: тот
сузил ключ до `A–Z a–z 0–9 . _ -`, что заново отвергло бы кириллицу и снесло
бы починку #75; этот запрет уже, специфичен и с #75 не пересекается — длина
по-прежнему считается в кодовых точках, набор писем не сужен.

У `X-Merchant-Id` запятая и так была вне допустимого набора с самого начала,
и это уже страховало его от точно такой же склейки дублей за прокси. Теперь
`Idempotency-Key` получает ту же страховку: запятая, попавшая в значение —
хоть от клиента, хоть от инфраструктурной склейки повтора, — теперь отклоняется
проверкой набора символов независимо от того, поймал ли её более ранний
разбор дублей по сырым заголовкам. Требование задним числом не отменяет
F7b — оно перестаёт зависеть от порядка проверок, чтобы держать один и тот же
случай.

Требование добавлено после находки QA (#73): дублирующийся `Idempotency-Key`
создавал два платежа, **оба с ответом 201**. Отказ был тихим — клиент не получал
никакого сигнала и узнал бы о двойном списании от своего пользователя, а не от API.
Явный 400 неудобен, но приходит немедленно и к тому, кто может исправить запрос.

### 5.2 Валидация

| # | Требование |
|---|---|
| F8 | `amount_minor` — целое число больше нуля в минорных единицах. Ноль, отрицательное, дробное, строка, значение за границей безопасного целого → 422 `validation_failed`, нарушение названо в `details.errors` |
| F9 | `currency` — код из белого списка (`RUB`, `USD`, `EUR`), регистр строгий. Иначе 422 `validation_failed`, нарушение названо в `details.errors` |

**Про коды валидации.** Первая редакция обещала отдельные коды `invalid_amount`
и `invalid_currency`; контракт (решение #32) свёл валидацию полей к одному 422
`validation_failed` с картой «поле → нарушение», отдающей **все** нарушения разом.
Прав контракт: интегратор чинит запрос за один заход, а не по одной ошибке за раз.
Различимость не потеряна — она переехала из кода ошибки в `details.errors`, и это
правильное место. 400 остаётся за тем, что не дошло до полей: заголовки
и неразобранное тело.

Расхождение прожило от #32 до независимой проверки API и было найдено третьей
стороной, а не автором требования и не автором кода. До того оно обходилось
примечанием «источник правды — контракт» в пяти задачах: обходной путь выглядит
как решение и работает как долг.
| F10 | `order_id` — непустая строка до 64 символов |
| F11 | `description` — необязательная строка до 512 символов. **Хранится и отдаётся как есть, не интерпретируется** ни сервером, ни клиентом |

### 5.3 Жизненный цикл

| # | Требование |
|---|---|
| F12 | `GET /v1/payments/{id}` отдаёт платёж. Несуществующий → 404 `payment_not_found` |
| F13 | `POST /v1/payments/{id}/cancel` переводит `pending` → `canceled`, отвечает 200 |
| F14 | Повторная отмена уже отменённого платежа → 200 и тот же результат (отмена идемпотентна) |
| F15 | Отмена платежа в терминальном статусе `succeeded` или `failed` → 409 `payment_not_cancelable` |
| F16 | `GET /v1/payments` отдаёт список платежей мерчанта — источник журнала в песочнице |
| F17 | Терминальный статус задаётся **детерминированным правилом по копейкам суммы** — таблица ниже. Правило применяется синхронно при создании |
| F18 | В ответе есть поле `status_reason`: `test_amount_rule`, если статус задан правилом, иначе `null` |
| F19 | **Маршрут проверяется первым.** Путь вне описанных → 404 `not_found`; описанный путь неописанным методом → 405 `method_not_allowed`. Этот 404 — «адреса нет» — не то же, что `payment_not_found` на описанном пути. `OPTIONS` под правила маршрутизации не попадает |
| F20 | Тело больше **1 МБ** не разбирается → 400 `malformed_request`. До **8 МБ** тело дочитывается и отбрасывается, чтобы ответ дошёл до клиента целым; выше — соединение рвётся |
| F21 | Длина строковых полей считается **в кодовых точках**, а не в кодовых единицах UTF-16 и не в байтах. Относится ко всем полям с ограничением длины: `Idempotency-Key`, `X-Merchant-Id`, `order_id`, `description` |
| F22 | `Content-Type` не `application/json` → 400 `malformed_request`. Отдельный код 415 **не вводится**: для клиента это та же ошибка запроса, а лишний код в контракте — лишняя ветка в каждой интеграции |

**Тестовые суммы.** Без них F15 непроверяем: ни один эндпоинт не порождает
`succeeded` и `failed`, потому что настоящие провайдеры за границей объёма.

| Последние две цифры `amount_minor` | Статус при создании |
|---|---|
| `01` | `failed` |
| `02` | `succeeded` |
| любые другие | `pending` |

Так устроены песочницы настоящих эквайреров — суммы и карты-триггеры. Отвергнуты:
симуляция по таймеру (тесты становятся ждущими и мигающими, проверка F15 —
гонкой) и отдельный эндпоинт `/simulate` (расширяет поверхность API ради одной
демонстрации при замороженном объёме).

Таблица обязана попасть в `openapi.yaml` и на страницу документации: бэкенд и фронт
берут её из одного источника, а не каждый из своей головы.

### 5.4 Формат ошибок

Единый по всему API: `{"error": {"code": "...", "message": "...", "details": {...}}}`.
Коды из требований выше — часть контракта и перечислены в `openapi.yaml`.

### 5.7 Запуск и воспроизводимость

Проверяющий не обязан иметь на машине ни Node, ни наших версий чего бы то ни было.
Единственное требование к нему — установленный Docker.

| # | Требование |
|---|---|
| R1 | `docker compose up` поднимает всё: API, песочницу, страницу документации. Больше ничего устанавливать не нужно |
| R2 | Порты фиксированы и перечислены в `README.md`; конфликт порта решается одной переменной окружения, а не правкой файлов |
| R3 | Образы собираются многоступенчато: сборка отдельно, запуск отдельно. В рантайме нет ни исходников тестов, ни `devDependencies` |
| R4 | Тесты запускаются в контейнере одной командой — `docker compose run --rm backend-test`. Образ для тестов отдельный: рантайм по R3 не содержит ни тестов, ни `devDependencies`, поэтому запустить их в нём нельзя. Локальный Node остаётся возможностью, а не условием |
| R5 | `README.md` содержит: предусловия, запуск, адреса, проверку работоспособности, остановку, пересборку и раздел «если не поднялось» с типовыми отказами |
| R6 | Данные живут в памяти контейнера: перезапуск обнуляет состояние, и это описано как ожидаемое поведение песочницы |

### 5.8 Откуда взялись F19–F22 и U7

Эти пять требований записаны **задним числом**, после прохода по принятым решениям
с одним вопросом: стоит ли за решением требование или оно держится на коде, тесте
и чьей-то памяти. Проход предложил проджект после случая, когда правка контракта
молча отменила уже принятую починку — та жила только в реализации.

Все пять описывают поведение, которое **уже реализовано и принято**: маршрутизация
и порядок проверок, предел на тело, счёт длины в кодовых точках, отказ от отдельного
415, изоляция управляющих символов направления в песочнице. Требований за ними
не стояло — они родились из находок ломателей и перекрёстных ревью, а не из PRD,
и потому в PRD не попали.

**Признак, по которому их искали:** если завтра кто-то сделает наоборот, узнаем ли
мы об этом от теста или от пользователя? Если от пользователя — нужно требование.
Внутренние решения (какой HTTP-слой, как разложены модули) в PRD не идут: их отмена
видна тому, кто отменяет.

## 6. Критерии приёмки

Работа считается сделанной, когда **каждый пункт подтверждён выводом команды**, а не
утверждением.

| # | Критерий | Чем доказывается |
|---|---|---|
| A1 | Два одинаковых запроса → один платёж, один `id` | `bash scripts/acceptance.sh` |
| A2 | Конфликт ключа → 409, платёж не изменился | `bash scripts/acceptance.sh` |
| A3 | Две одновременные отправки → один платёж | тест на гонки в `npm test` |
| A4 | Все границы из раздела 5 покрыты тестами | `npm test`, зелёный прогон |
| A5 | Песочница показывает A1 и A2 без чтения логов | скриншот или запись экрана в отчёте |
| A6 | Страница документации собрана из `openapi.yaml` | команда сборки в README |
| A7 | Поведение API соответствует `openapi.yaml` | проверка контракта в CI |
| A8 | Инструкция из `README.md` работает на чистом клоне: `git clone` во временную папку, `docker compose up`, сценарий A1 проходит | прогон в свежей папке, вывод в отчёте |
| A11 | Тесты проходят внутри контейнера, а не только на машине автора | `docker compose run --rm backend-test` |
| A12 | Платёж с копейками `02` уходит в `succeeded`, его отмена даёт 409 `payment_not_cancelable` | тест + пресет в песочнице |
| A13 | Запрос без `X-Merchant-Id` отклоняется, одинаковый ключ у двух мерчантов даёт два разных платежа | тест + переключатель мерчанта в песочнице |
| A9 | CI зелёный на pull request | `gh pr checks` |
| A10 | `description` с разметкой и скриптом не исполняется ни в API, ни в песочнице | тест + проверка в браузере |

## 7. Риски

| Риск | Что делаем |
|---|---|
| Идемпотентность «на глаз»: проверка и запись без атомарности | F4 закрывается тестом на гонки до реализации, а не после |
| Фронт и бэк расходятся: сессии не видят друг друга | контракт `openapi.yaml` пишется до реализации, спор решается файлом |
| Объём расползается на «ещё одну фичу» | раздел «не входит» — часть приёмки, а не пожелание |
| Ролевое разделение превращается в театр | задание и приёмка — файлами в `docs/tasks/`, приёмку делает не автор |
| `description` как вектор атаки | F11, U6, A10 — три разных проверки одного поля |
