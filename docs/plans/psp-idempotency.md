# ДЗ №2 · Идемпотентный платёжный сервис: API, песочница, документация

## Контекст

В репозитории стоит обвязка и нет продукта: восемь хуков, workflow `/feature`, внешний
ревьюер на `codex`, CI. Пункт 3 задания (workflow) закрыт файлом
`.claude/workflows/feature.js`, пункт 2 (агенты) закрывается по ходу, **пункт 1 —
работающий результат — отсутствует**. `.ci-stack` содержит `none`, шаги сборки честно
объявляют себя пропущенными.

Делаем идемпотентный платёжный сервис из трёх частей: **API**, **песочница**, где это
поведение можно потрогать руками, и **документация по контракту**. Тема — вариант C1
задания; выбрана потому, что идемпотентность это место, где агент чаще всего пишет
правдоподобный, но неверный код, а песочница показывает не красоту, а поведение системы:
нажал «отправить» дважды — платёж остался один.

Работа ведётся соло, но **обязанности разнесены по отдельным сессиям**: продукт, проджект,
дизайнер, бэкендер, фронтендер, QA. Сессия не видит контекста другой сессии, поэтому
передача идёт письменным заданием в git, а не общей памятью. Это ближе к настоящей
независимости, чем субагенты внутри одного контекста, и оставляет в репозитории цепочку
артефактов. **В `README.md` это называется своим именем: соло с ролевым разделением
сессий, не команда людей.**

## Продукт: вертикальный срез в один сценарий

Границу объёма ставим здесь и не двигаем: ТЗ прямо предупреждает, что маленькая вещь
до конца лучше большой наполовину.

### Бэкенд — `backend/`

| Метод | Путь | Поведение |
|---|---|---|
| `POST` | `/v1/payments` | `Idempotency-Key` обязателен. Тело: `amount_minor`, `currency`, `order_id`, `description`. 201 |
| `POST` | `/v1/payments` (повтор) | Тот же ключ + то же тело → 200 и **тот же ресурс**, второго платежа нет |
| `POST` | `/v1/payments` (конфликт) | Тот же ключ + другое тело → 409 `idempotency_key_reuse` |
| `GET` | `/v1/payments/{id}` | Статус: `pending` → `succeeded` / `failed` / `canceled` |
| `POST` | `/v1/payments/{id}/cancel` | Отмена из `pending`, повторная отмена идемпотентна, отмена завершённого → 409 |
| `GET` | `/v1/payments` | Список для журнала песочницы |

Границы, каждая — тест:

1. тот же ключ + то же тело → ровно один платёж, ответ повторяется байт-в-байт;
2. тот же ключ + другое тело → 409, существующий платёж не меняется;
3. две одновременные отправки с одним ключом → один платёж (тест на параллельных запросах);
4. повтор, пока первый в полёте → 409 `request_in_progress`, а не второй платёж;
5. TTL ключа: после истечения ключ переиспользуем;
6. ключ скоупится по мерчанту — чужой ключ не трогает чужой платёж;
7. сумма: ноль, отрицательная, дробная, строкой, за границей безопасного целого;
8. валюта: неизвестная, в нижнем регистре, пустая;
9. отмена дважды, отмена завершённого, отмена несуществующего;
10. `description` — недоверенный текст: хранится и отдаётся, но **не исполняется**
    ни сервером, ни фронтом (граница XSS и граница инъекции разом).

### Песочница — `frontend/`

Один экран, по которому видно поведение, а не витрина:

- форма: сумма, валюта, `order_id`, описание, ключ идемпотентности с кнопкой «сгенерировать»;
- две кнопки: «Отправить» и **«Отправить ещё раз тот же запрос»**;
- журнал обмена: запрос, код ответа, время, `id` платежа — с явной пометкой
  «тот же платёж» против «новый платёж»;
- готовые сценарии одной кнопкой: повтор с тем же телом · тот же ключ и другое тело · две
  одновременные отправки · двойная отмена;
- список платежей сбоку — чтобы было видно, что он не растёт от повторов.

### Документация — `openapi/` и страница

`openapi.yaml` (OpenAPI 3.1) — **единственный источник правды для трёх ролей сразу**:
бэкенд проверяется на соответствие, фронт берёт типы, страница документации генерится
из него. Спор двух сессий решается файлом, а не перепиской. Страница — Scalar,
собирается в статику.

## Роли, сессии и передача работы

| Роль | Что делает | Вход | Выход в git |
|---|---|---|---|
| **Продукт** (эта сессия) | что делаем и зачем, критерии приёмки | задание курса, разговор с сэром | `docs/product/PRD.md`, этот план |
| **Проджект** (новая сессия) | режет на задачи, назначает порядок, принимает работу | PRD | GitHub Issues по шаблону `.github/ISSUE_TEMPLATE/role-task.yml`, метки `role:*`, приёмка комментарием |
| **Дизайнер** (новая сессия) | макет песочницы и страницы доков, токены | задание проджекта | `design/` — макет, палитра, типографика, состояния |
| **Бэкендер** (worktree) | API и тесты | задание + PRD + черновик контракта | `backend/`, `openapi/openapi.yaml` |
| **Фронтендер** (worktree) | песочница по макету и контракту | задание + `design/` + `openapi.yaml` | `frontend/` |
| **Документация** (worktree) | страница Scalar, примеры вызовов | `openapi.yaml` | `docs-site/` |
| **QA-ломатель** (отдельная сессия) | ломает сервис, не чинит | работающий сервис | `docs/reviews/breaker.md` |

Правила ролевой игры, без которых она превращается в театр:

- **Задание передаётся письменно — issue по шаблону.** Устная передача в чате
  не считается: проверяющий должен видеть цепочку PRD → задача → pull request →
  приёмка. Структура задания задана файлом в git, сами задачи — в GitHub Issues.
- **Исполнитель не читает чужие сессии.** Вопрос задаётся заданием или прямым сообщением
  между сессиями (канал проверен: `ListAgents` видит соседние сессии на этой машине).
- **Приёмку делает не автор.** Работу бэкендера принимает проджект и ломает QA.
- **Каждая роль пишет в свой файл журнала** `sessions/<роль>.md` — дословные промпты
  и решения.

## Стек

| Часть | Решение | Почему |
|---|---|---|
| Бэкенд | **TypeScript + Node 22**, тесты `node:test` | Типы контракта общие с фронтом: расхождение между сессиями ловит компилятор, а не глаз |
| Фронт | **React + Vite + TypeScript** | Макет ложится на компоненты один в один, сборка в статику |
| Контракт | **OpenAPI 3.1** | Машиночитаемая граница между тремя ролями |
| Документация | **Scalar** | Страница из контракта, без ручной синхронизации |
| Запуск | **Docker + compose** | Проверяющему нужен только Docker: `docker compose up` поднимает API, песочницу и документацию. Ни Node, ни версий, ни «допишите тут своё» |
| CI | `.ci-stack` → `node` | Команды вписываются в `scripts/ci/{test,lint,analyse}.sh`, после чего пропуск шага становится ошибкой сборки |

Выбор HTTP-слоя (Fastify против голого `node:http`) и хранилища (память против `node:sqlite`)
оставляем бэкенд-сессии — это её зона, обсуждается при постановке задачи.

## Порядок работ

**Сессия 1 · Продукт (текущая).** PRD с критериями приёмки. Структура репозитория.
Правка `.claude/hooks/mark-verify.py` — файл защищённый, потребует подтверждения:
сейчас `gate-quality` не считает тестами ни `python3 -m unittest`, ни собственные
`scripts/test_*.py`, поэтому блокирует завершение любой сессии, где трогали код.
Дефект найден в этой сессии, воспроизведён; регрессионный тест — в `scripts/test_hooks.py`.

**Сессия 2 · Проджект.** Читает PRD, режет на задачи с явными зависимостями, пишет
`docs/tasks/`. Первым делом — черновик `openapi.yaml`, чтобы дизайнер, бэк и фронт
работали от одного контракта.

**Сессия 3 · Дизайнер.** Макет песочницы и страницы документации: сетка, палитра,
типографика, состояния ответа (успех, повтор, 409, ошибка сети), компоненты. Формат
макета выбирается в самой сессии — кандидаты: design-canvas или HTML-прототип.

**Сессия 4 · Бэкенд** (worktree `feature/backend-api`). Тесты вперёд, каждая граница
из списка — отдельный тест. Финал: `openapi.yaml` соответствует поведению.

**Сессия 5 · Фронт** (worktree `feature/frontend-sandbox`). Песочница по макету и
контракту. Проверка на живом бэкенде, а не на моках.

**Сессия 6 · Документация** (worktree `feature/docs-openapi`). Страница Scalar, примеры
`curl`, раздел про идемпотентность человеческим языком.

**Сессия 7 · Проверки чужими руками.** QA-ломатель (10+ итераций, отдельная сессия).
Внешнее ревью: `python3 scripts/review_codex.py --timeout 900 "<ревью кода>"`. Инъекции:
пять способов внедрения в `description`, `order_id`, метаданные, CSV-выгрузку, HTML-отчёт;
одна задача прогоняется на Opus 5, Haiku 4.5 и codex; таблица «способ × модель →
выполнила / промолчала / **назвала вслух**». Изоляция: `/sandbox`, попытка выйти
за границу, в отчёт идёт **вывод отказа**; отдельно — проверка, что песочница не накрывает
MCP. Замеры: та же работа веером и последовательно, время и контекст.

**Сессия 8 · Сдача.** `README.md` (проверяется на чистом клоне, а не по памяти),
`REPORT.md` по каждому пункту включая несработавшее, `sessions/`, PDF из отчёта,
финальная проверка на секреты.

## Структура репозитория

```
backend/        API на TypeScript, тесты рядом с кодом
frontend/       песочница React + Vite
docs-site/      страница документации Scalar
openapi/        openapi.yaml — контракт
design/         макет и токены
docs/
  product/PRD.md          продуктовое задание
  tasks/                  задания ролям и приёмка
  plans/                  планы (этот файл)
  reviews/                ревью, находки ломателя, сравнения
  injections/             датасет инъекций и таблица результатов
sessions/       журналы по ролям, дословные промпты
```

Переиспользуем существующее, а не пишем заново: `.claude/workflows/feature.js` (полный
цикл до PR), `scripts/review_codex.py` и `.claude/schemas/review.json` (внешний ревьюер),
`scripts/scan_untrusted.py` (проверит наш же датасет инъекций), `scripts/test_hooks.py`.

## Как проверяется

```bash
docker compose up                              # API, песочница, документация — всё сразу
docker compose run --rm backend npm test       # тесты внутри контейнера
bash scripts/acceptance.sh                     # curl: создать, повторить, статус, отменить
python3 scripts/test_hooks.py                  # обвязка цела
python3 scripts/ci/scan_secrets.py             # секретов нет
```

Локальный запуск без Docker (`npm ci && npm run dev` в `backend/` и `frontend/`)
остаётся возможностью для разработки, но инструкция сдачи опирается на Docker:
у проверяющего не должно быть ни одного предусловия, кроме него.

Критерий готовности: два одинаковых запроса дают один платёж и **один и тот же `id`**;
конфликт ключа даёт 409; две одновременные отправки дают один платёж; песочница это
показывает без чтения логов; страница документации собрана из того же `openapi.yaml`,
которому соответствует бэкенд; CI зелёный на pull request; `README.md` проверен на чистом
клоне.

## Чего не делаем

Аутентификации мерчантов сверх заголовка, базы данных сверх встроенной, вебхуков,
личного кабинета, деплоя на сервер, мобильного клиента. И не выдаём ролевые сессии
за команду людей.

Docker, наоборот, входит в объём: он и есть инструкция запуска.
