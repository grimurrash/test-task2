## 1. F20 — три полосы тела

**Требование.** Тело больше 1 МБ не разбирается → 400 `malformed_request`;
до 8 МБ дочитывается и отбрасывается, чтобы ответ дошёл целым; выше — обрыв.

**Сейчас.** Закрыта одна полоса: `backend/test/validation.test.ts:401` шлёт
~2 МБ и ждёт 400. `MAX_DRAIN_BYTES` (`backend/src/app.ts:34`) не назван нигде.

**Делаю.** Новый файл `backend/test/body-limits.test.ts`, три теста:

| Полоса | Тело | Чего ждём |
|---|---|---|
| < 1 МБ | `description` ~900 000 ASCII-символов (≈900 КБ) | тело **разобрано**: 422 `validation_failed` с нарушением по `description`, а не 400 |
| 1–8 МБ | `description` ~3 000 000 символов (≈3 МБ) | 400 `malformed_request`, **ответ дошёл целым**: тело — разбираемый JSON, конверт `schemas/Error` полон, соединение не оборвано |
| > 8 МБ | ~9 МБ | запрос **не получает ответа**: `fetch` отвергается сетевой ошибкой, а не отдаёт 400 |

Разговор с сервером — через обвязку (`app.raw` / `app.create`), сырой клиент
не заводится: маркер `raw-http-client: allowed` не нужен, `hygiene.test.ts`
остаётся коротким.

Полоса «< 1 МБ» доказывается кодом **422**, а не 201, намеренно: 422 приходит
из валидации полей, то есть тело было разобрано. 201 доказывал бы то же самое
слабее — его дал бы и сервер, вовсе не читающий тело.

**Обратная проверка.** Снять `MAX_DRAIN_BYTES` (убрать ветку обрыва) → полоса
«> 8 МБ» краснеет. Сдвинуть обрыв на `MAX_BODY_BYTES` → краснеет полоса 1–8 МБ.

## 2. U4 — инвариант гонки вместо кода ответа

**Требование.** Готовые сценарии одной кнопкой, включая «две одновременные
отправки». Продуктовое решение (REPORT 4.7): искусственную задержку не
добавлять, показывать инвариант, а не код ответа.

**Сейчас.** Оба исхода (`201/200`, `201/409`) законны, и набор не отличает
«выпал другой законный исход» от «появился второй платёж».

**Делаю.** Новый `frontend/src/test/u4-race.test.tsx`. Вместо мока «ответ
на каждый POST» — **поддельный бэкенд** в тесте: маленькое идемпотентное
хранилище «ключ → платёж», отвечающее на POST `/v1/payments` и GET
`/v1/payments`. Режим исхода второго запроса — параметр: `'200'` (первый уже
зафиксирован) и `'409'` (`request_in_progress`, первый ещё в полёте).

Тест гоняет **обе** ветки через `it.each` и на каждой закрепляет инвариант:

- в журнале ровно один `id` платежа — множество увиденных `id` имеет размер 1;
- поддельный бэкенд создал ровно один платёж (счётчик созданий = 1);
- список платежей после сценария — из одной карточки, счётчик в заголовке `· 1`.

Третий случай — **подмена, дающая второй `id`** — в тест не входит; это
обратная проверка, см. ниже.

Почему поддельный бэкенд, а не мок ответов: мок, отдающий заранее написанные
`id`, закрепляет собственную выдумку. Инвариант «платёж один» проверяем на
чём-то, что **умеет** создать второй, — иначе тест не может покраснеть.

**Обратная проверка.** Сделать поддельный бэкенд неидемпотентным (второй POST
создаёт второй платёж) → тест краснеет на обеих ветках. Сменить режим исхода
`200` → `409` → тест **не** краснеет.

## 3. U7 — изоляция в списке платежей

**Требование.** Значения, пришедшие от сервера, изолируются от управляющих
символов направления письма.

**Сейчас.** `unicode-bidi: isolate` объявлен один раз — на `.chip`
(`frontend/src/app.css:269`); `<bdi>` — только в журнале
(`Journal.tsx:48`). В `PaymentsList.tsx` под `.chip` попадает лишь `p.id`;
`order_id` (`span.mono`) и `description` (`p.desc`) не изолированы ничем.

**Делаю.**

1. `frontend/src/components/PaymentsList.tsx`: значения сервера — `order_id`,
   `description`, `status_reason` — в `<bdi>`, по образцу журнала. Значение
   не фильтруется и не изменяется: показ «как есть» (F11/U6) сохраняется,
   изолируется только окружение.
2. `frontend/src/app.css`: правило `unicode-bidi: isolate` для `bdi` в карточке
   платежа — jsdom не применяет UA-стиль `bdi`, а браузеру нужен явный якорь,
   который видно при удалении.
3. Новый `frontend/src/test/u7-list-bidi.test.tsx` по образцу `bidi.test.tsx`:
   платёж с `U+202E` в `description` — значение лежит в `<bdi>` байт-в-байт,
   соседние `order_id` и сумма — **вне** этого изолята (то есть перевернуть их
   нечем), и `app.css` объявляет изоляцию для `bdi` карточки.

**Обратная проверка.** Снять `<bdi>` в `PaymentsList.tsx` → тест краснеет.
Снять правило из `app.css` → краснеет вторая половина теста.

## 4. A4 — машинная сверка «требование → тест»

**Критерий.** Все границы из раздела 5 PRD покрыты тестами, зелёный прогон.

**Сейчас.** Это утверждение, а не проверка: ни один прогон не падает, если
требование останется без теста.

**Делаю.**

**Перечень — из PRD, закрытый.** Новый `backend/test/requirements-coverage.test.ts`
читает `docs/product/PRD.md`, берёт участок от `## 5.` до `## 6.` и вынимает
идентификаторы из первой колонки таблиц по образцу `^[FURD]\d{1,2}[a-c]?$`.
Сегодня это 43 требования: F1–F22 с F7a/F7b/F7c (25), U1–U7 с U4a (8),
D1–D4 (4), R1–R6 (6). Список нигде не выписан руками — **новое требование
в PRD попадает в перечень само**.

**Привязка — пометкой в тесте.** Токен `@req <ID>` в тексте файла теста
(в имени теста или в комментарии рядом). Сканируются `backend/test/**/*.ts`
и `frontend/src/test/**` — оба набора, потому что U-требования проверяются
фронтом.

**Сверка падает в четырёх случаях**, и это её содержание:

1. у требования из PRD нет ни одной пометки — названо поимённо;
2. пометка ссылается на идентификатор, которого в PRD нет (устаревшая
   привязка — обратное направление той же дыры);
3. перечень требований пуст или подозрительно мал (< 40) — разбор PRD сломался;
4. каталог тестов не найден или пуст.

Третий и четвёртый пункта — тот самый **третий исход** из REPORT 4.14:
«проверять было нечего» обязано быть отказом, а не зелёным.

**Расстановка пометок.** У 22 требований тесты уже есть и опознаются по
существующим именам — им дописывается токен. Остальным пометка ставится там,
где поведение действительно проверяется:

- F19, F21, F22, F7b, F7c — существующие тесты `http.test.ts`, `headers.test.ts`,
  `validation.test.ts`;
- F20 — новый `body-limits.test.ts` (п. 1);
- U4, U5 — новый `u4-race.test.tsx` (п. 2); U7 — новый `u7-list-bidi.test.tsx` (п. 3);
- U1, U4a — два небольших теста песочницы: состав полей формы с кнопкой
  генерации ключа; переключение мерчанта меняет `X-Merchant-Id` в запросе;
- D1–D4, R1–R6 — новый `backend/test/delivery.test.ts`, проверки **по артефактам,
  а не по прозе**: маршруты и коды ошибок сервера описаны контрактом (D1);
  страница собирается из `openapi/openapi.yaml` и своего перечня эндпоинтов
  не держит (D2); в контракте есть раздел «Идемпотентность», и он говорит
  про ключ, TTL, конфликт и гонку (D3); каждый блок `curl` в
  `docs-site/src/scenarios.md` бьёт по маршруту и методу, описанным контрактом,
  и обещанный им код ответа контрактом описан (D4); `compose.yaml` поднимает
  три части одной командой (R1); порты вынесены в переменные и названы в README
  (R2); рантайм-цель `backend/Dockerfile` не несёт ни тестов, ни зависимостей
  разработки (R3); `backend-test` — отдельная цель и сервис (R4); README
  содержит требуемые разделы, включая «если не поднялось» (R5); README называет
  обнуление состояния при перезапуске, а `compose.yaml` не заводит томов
  под данные (R6).

Эти тесты читают файлы репозитория, поэтому в контейнер репозиторий
монтируется на чтение: в `compose.yaml` сервису `backend-test` добавляется
`- .:/app/repo:ro` и `REPO_ROOT=/app/repo`. Корень ищется по `REPO_ROOT`,
иначе — подъёмом от каталога теста до `docs/product/PRD.md`; не нашёлся —
громкий отказ, не пропуск. Прецедент в наборе есть: `test/support/contract.ts`
так же читает контракт и так же отказывается работать без него.

**Обратная проверка.** Снять пометку с любого теста → сверка краснеет и
называет требование. Дописать в PRD строку `| F23 | ... |` → сверка краснеет
на новом требовании (доказательство закрытости перечня). Пометка на
несуществующий `F99` → сверка краснеет.

## 5. A7 — сверка заголовков с контрактом

**Критерий.** Поведение API соответствует `openapi.yaml`, проверка в CI.

**Сейчас.** Сверяются тела запросов и ответов; схемы параметров
`IdempotencyKey`, `XMerchantId`, `PaymentId` не проходят через валидатор ни разу
(REPORT 4.13: ветка с прежним контрактом дала 232/232 зелёных, включая четыре
теста, которые контракт прямо запрещает).

**Делаю.** Новый `backend/test/contract-headers.test.ts`. Для каждого параметра
берётся **схема из контракта** и фиксированный набор проб — пустая строка,
1 символ, ровно граница, граница+1, 255 кириллических символов (починка #75),
значения с запятой, пробелом, `/`, `%`, эмодзи, обычное демо-значение. Каждая
проба проходит две линзы:

- **контракт**: валидна ли она по схеме параметра (ajv, тот же валидатор);
- **код**: принял сервер запрос или отверг его отказом **по форме этого
  заголовка** (`invalid_idempotency_key` / `idempotency_key_required` /
  `invalid_merchant_id` / `merchant_id_required`).

Свойство жёсткое и двустороннее: **проба валидна по контракту тогда и только
тогда, когда сервер её не отверг**. Расхождение в любую сторону — красный тест
с названной пробой и вердиктами обеих линз.

Для `PaymentId` (параметр пути) «отказ по форме» — это 400; сегодня контракт
не ограничивает его ничем, сервер по форме не отказывает, обе линзы согласны.
Появится в контракте `pattern` — проба его нарушит, и сверка покраснеет.

Заголовки шлются сырым сокетом: `fetch` не пропускает не-ASCII в значении
заголовка (та же причина, по которой существует `headers.test.ts`). Поэтому
файл объявляет маркер `raw-http-client: allowed` в шапке — как того требует
`hygiene.test.ts`, а не в обход него.

**Про F7c — называется вслух, не чинится.** Проверено при разборе: у
`IdempotencyKey` в контракте только `minLength: 1` и `maxLength: 255`,
`pattern` нет — то есть набор символов сегодня не сужен и расхождения
с F7c нет. Сверка это закрепляет: появится `pattern`, запрещающий кириллицу, —
проба «255 кириллических символов» разведёт линзы и покрасит тест. Приводить
код к контракту в такой ситуации запрещено: расхождение выносится в PR словами.

**Обратная проверка.** Дописать `pattern: '^[A-Za-z0-9._-]+$'` в схему
`IdempotencyKey` → тест краснеет на кириллической пробе (контракт запрещает,
код принимает). Сменить `maxLength` на 64 → краснеет на пробе в 255 символов.

## 6. A8 — повторяемый прогон на чистом клоне

**Критерий.** Инструкция из `README.md` работает на чистом клоне.

**Сейчас.** Прогон сделан однажды руками (REPORT 2.1), порядок шагов живёт
в прозе.

**Делаю.** `scripts/clean-clone-check.sh` — делает всё сам:

1. проверяет предусловия: `docker`, `git`, свободные порты;
2. клонирует репозиторий (по умолчанию — текущий, `--ref` задаёт ветку)
   во временный каталог;
3. убеждается, что клон не пуст и несёт `compose.yaml`, `README.md`,
   `scripts/acceptance.sh`;
4. поднимает стенд по README — `docker compose up -d --build` на своих портах,
   ждёт `healthy` бэкенда с потолком по времени;
5. гонит `bash scripts/acceptance.sh` **из клона** против поднятого стенда;
6. убирает за собой всегда — `docker compose down --rmi local -v`, удаление
   временного каталога — через `trap`.

**Три исхода, а не два** (REPORT 4.14, #127):

| Код | Смысл | Когда |
|---|---|---|
| 0 | сошлось | приёмка прошла, расхождений нет |
| 1 | разошлось | приёмка нашла расхождение |
| 2 | **проверять было нечего** | нет docker/git, порт занят, клон пуст, образ не собрался, стенд не стал `healthy`, приёмка не запустилась |

Ноль печатается только вместе с числом выполненных шагов приёмки: «прошло 0
проверок» кодом 0 не заканчивается никогда.

**Обратная проверка.** Запуск с занятым портом → код 2 и внятная причина,
а не 0. Запуск с `--ref` на несуществующую ветку → код 2. Приёмка, сломанная
подменой ожидания, → код 1. Успешный прогон целиком → код 0, вывод в PR.
