# Workflow `/feature`

Повторяемая процедура для любой задачи, доходящей до кода и до pull request.
Файл: [`.claude/workflows/feature.js`](../.claude/workflows/feature.js).

Уровнем выше стоит схема из двух ролей: координатор раздаёт задачи, исполнители
их делают. `/feature` — то, чем работает исполнитель внутри своей сессии;
см. [«Две роли»](#две-роли) ниже, [регламент координатора](roles/karina.md)
и [регламент исполнителя](roles/executor.md).

## Запуск

```
/feature Добавить идемпотентность в создание платежа
```

Или напрямую, если нужно задать ветку и slug:

```
Workflow({ name: "feature", args: { task: "...", slug: "idempotency", base: "main" } })
```

## Ступени

| # | Ступень | Кто делает | Что остаётся на диске |
|---|---|---|---|
| 1 | План | один агент | `docs/plans/<slug>.md` |
| 2 | Ревью плана | три независимых агента: архитектура, риски, объём | вердикты в журнале прогона |
| 3 | Правка плана | один агент сводит замечания | обновлённый план + раздел «Отклонённые замечания» |
| 4 | Реализация | один агент по утверждённому плану | ветка `feature/<slug>`, коммиты, тесты |
| 5 | Ревью результата | две линзы Claude (корректность, тесты) плюс внешний ревьюер на codex | список дефектов с пометкой, чья линза нашла |
| 6 | Исправления | один агент | коммиты с исправлениями |
| 7 | MR | один агент | pull request через `gh pr create` |
| 8 | CI | один агент | вердикт по проверкам, разбор падений |

Ступени 2–3 крутятся до двух раундов: пока остаются замечания уровня `blocker`
или `major`, план возвращается на правку.

## Три решения, которые здесь зашиты

**Ревьюеров трое, и у каждого своя линза.** Три одинаковых проверяющих находят
одно и то же. Архитектура, риски и объём — разные вопросы к одному тексту.

**Проверяет не автор.** Ступени 5–6 отданы агентам, которые код не писали. Автор
не бывает независимым проверяющим — он проверяет то, что имел в виду, а не то,
что написал.

**Третий проверяющий — другой вендор.** Субагент видит контекст родительской
сессии: это приближение к независимой проверке, а не она сама. Поэтому третья
линза ступени 5 уходит наружу — в `codex exec`, read-only, со структурированным
вердиктом по `.claude/schemas/review.json`. Обёртка: `scripts/review_codex.py`.

Задание внешнему ревьюеру формулируется как обычное ревью кода. Просьбу
«найди способ обойти защиту» провайдер отклоняет фильтром как разработку обхода:
проверено на практике, вердикт возвращается пустым. Та же проверка, названная
своим именем — «оцени корректность и полноту защитных проверок», — проходит
и даёт находки.

Если codex не установлен, не авторизован или не уложился в срок, обёртка
возвращает `verdict: unavailable` с причиной. Workflow при этом не падает,
но пишет в лог и в тело PR, что проверка осталась внутримодельной. Молча
деградировать до «сам себя проверил» — худший из возможных исходов.

**Замечание нельзя проигнорировать молча.** На каждое — либо правка, либо
письменное обоснование отказа в плане. Молчание не считается ответом.

## Что нужно до запуска

- `gh` установлен и авторизован: `gh auth status`. Ступень 7 останавливается
  сама и возвращает точную команду, если авторизации нет.
- `codex` установлен и авторизован: `codex login status`. Без него ступень 5
  теряет внешнюю линзу, но не останавливается.
- Ветка `main` чистая, работа начинается от неё.

Проверить внешнего ревьюера отдельно, без всего workflow:

```bash
python3 scripts/review_codex.py "Проверь .claude/hooks на способы обхода запретов"
```

## Чего workflow не делает

Не мержит. Ступень 8 доводит до зелёного CI и останавливается. Решение
о слиянии принимает тот, кто запускал: в одиночной работе — сэр, в схеме
из двух ролей — сессия-исполнитель, после зелёного CI и закрытых замечаний.

## Две роли

Схема, пришедшая на смену пятнадцати ролевым сессиям 25 августа. Разбор той
смены — [multisession.md](../multisession.md); здесь оставлено то, что она
подтвердила, и убрано то, за что она заплатила.

| | Координатор (Карина) | Исполнитель (Рустем, Салават, …) |
|---|---|---|
| Сколько | одна, живёт постоянно | одна на задачу, умирает после рапорта |
| Где | основная копия, ветка `chore/journal` | своя копия `.worktrees/<slug>` |
| Запускает | сэр: «Карина, начинаем работать» или `/karina` | Карина: `claude --bg -n "<Имя>"` |
| Делает | тикет, запуск, приём рапорта, закрытие, `REPORT.md` | всё от разбора задания до слияния PR |
| Не делает | код, перепроверку работы, выдачу пропусков | закрытие тикета, разговор с сэром напрямую |
| Регламент | [roles/karina.md](roles/karina.md) | [roles/executor.md](roles/executor.md) |

Поток одной задачи:

```
сэр → Карина          задача словами
Карина → gh           issue #N
Карина → git          .worktrees/<slug>, ветка <type>/<slug> от main
Карина → claude --bg  сессия «<Имя>» с заданием и адресом координатора
<Имя> → Карина        «взял #N»                        ← приём, иначе тихая остановка
<Имя>                 /feature: план → ревью → код → ревью → PR → CI
<Имя> → gh pr merge   слияние после зелёного CI
<Имя> → Карина        рапорт: что сделано, чем проверено, что мешало
Карина → gh           проверка факта слияния, issue close, worktree remove
Карина → сэр          доклад; строка в REPORT.md
```

### Почему именно так

**Проверяет тот, кому не показали замысел.** Единственное, что прошлая смена
дала однозначно ценного. Поэтому ревью живёт внутри сессии исполнителя (три
линзы на план, две плюс внешняя на результат), а координатор в него не лезет:
его проверка была бы третьей проверкой того же замысла, а не независимой.

**Координатор — сессия, а не человек.** Человек в роли маршрутизатора был
потолком схемы: пятнадцать сессий на одного — очередь, а не масштабирование.
Сэр остаётся там, где его нельзя заменить: постановка задачи, выдача пропусков,
приоритеты.

**Своё состояние каждому.** Своя копия, своя ветка, своя запись в `verify.json`
по идентификатору сессии. Разделяемое состояние без владельца было самой дорогой
статьёй прошлой смены — три дефекта заведены на саму обвязку.

**Канал должен использоваться, а не существовать.** Прямая связь между сессиями
за прошлую смену упомянута пять раз на 7283 строки журналов, то есть её не было.
Здесь она обязательна в трёх точках: приём задачи, просьба о пропуске, рапорт.
Каждая из них — механизм против тихой остановки, а не вежливость.

### Чего схема по-прежнему не умеет

Контрольной группы не было и здесь: сколько бы сделала одна сессия за то же
время, неизвестно. Схема оправдана там, где цена ошибки выше цены круга
проверки, и убыточна на задаче, укладывающейся в одну сессию, — тогда
координация чистый расход.
