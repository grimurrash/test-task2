# Хуки: правила, переведённые в механизм

На первом занятии агент удалил папку, хотя в `CLAUDE.md` было написано не удалять.
Разбор свёлся к формулировке: «она была мягкой». Это половина причины. Вторая —
словесный запрет действует ровно до первого текста, который окажется убедительнее.

Поэтому здесь правила живут не в прозе, а в коде. Всё, что описано ниже, проверено
запуском: `python3 scripts/test_hooks.py` — 27 проверок.

## Что стоит

| Хук | Событие | Что делает |
|---|---|---|
| `guard-secrets.py` | PreToolUse: Bash, Read, Grep, Glob, Write, Edit | Блокирует обращение к `.env`, `~/.ssh`, `~/.aws`, ключам, глобальным настройкам Claude Code, `sudo` |
| `guard-git.py` | PreToolUse: Bash | Блокирует force-push, `--no-verify`, `filter-branch`, удаление защищённых веток. Отказывает без пропуска на push в защищённую ветку — по имени в тексте команды **и** по факту (HEAD рабочего дерева, где выполнится push), `reset --hard`, `clean -f`, создание ветки вне соглашения, worktree |
| `guard-scope.py` | PreToolUse: Bash, Write, Edit | Блокирует запись и удаление за пределами репозитория. Граница — общий корень с любым linked worktree (`git rev-parse --git-common-dir`), не то, что случайно лежит в `CLAUDE_PROJECT_DIR` |
| `guard-protected-files.py` | PreToolUse: Bash, Write, Edit | Отказывает в правке `.claude/`, `.github/workflows/`, `CLAUDE.md`, `scripts/unlock.sh` — и файловыми инструментами, и командой (`sed -i`, перенаправление, встроенный код). Разрешение — только пропуск. Корень — тот же общий, что у `guard-scope.py` |
| `scan-untrusted.py` | PostToolUse: Read, WebFetch, WebSearch, Bash (только `gh issue view/list/comment`, `gh pr view`, `curl`, `wget`) | Ищет скрытые инструкции в прочитанном и называет их вслух |
| `mark-verify.py` | PostToolUse: Bash | Фиксирует факт прогона тестов и анализаторов |
| `gate-quality.py` | Stop | Не даёт закрыть сессию с незакоммиченным кодом или без прогона тестов. Признаёт репозиторием и linked worktree (`.git` там — файл, не папка) |
| `session-start.sh` | SessionStart | Печатает приоритет инструкций, проверяет целость обвязки, линтует `CLAUDE.md` |

## Почему не хватило permissions

Правило `deny` — это шаблон на строку команды. Запрет `cat secrets.txt` не мешает
прочитать тот же файл через Python. Проверка в `scripts/test_hooks.py` ровно это
и воспроизводит: `python3 -c "print(open('.env').read())"` получает отказ, потому
что хук смотрит на упоминание пути, а не на имя команды.

Уточнение к тому, что звучало на занятии: `deny`-правила действуют во всех режимах,
включая `bypassPermissions`; отключаются только `allow` и `ask`. Поэтому в
`.claude/settings.json` лежат оба слоя — и `deny`, и хуки.

## Как ослабить запрет

Регулярка в `.claude/guard-allow.txt` снимает блокировку по совпадению с командой
или путём. По одной строке на случай, с комментарием зачем. Не «разрешить всё».
На защищённые файлы этот клапан не действует: постоянное исключение для файла
правил — это и есть снятие защиты.

## Пропуск вместо подтверждения

Решение хука `ask` показывает диалог — если среде есть кому его показать. В сессии
через Agent SDK, в headless-прогоне и в CI подтверждать некому, и `ask` **пропускает
команду**, оставляя в журнале только след. Проверено 25 августа: правка защищённого
хука и создание ветки прошли именно так.

Поэтому `ask` в этом репозитории не используется. Операции, которые раньше
переспрашивали, теперь отказывают, а разрешение выдаётся заранее — отдельным
сознательным действием сэра:

```bash
bash scripts/unlock.sh protected-files 15 "починка mark-verify"
bash scripts/unlock.sh --list
bash scripts/unlock.sh --revoke protected-files
```

| Зона | Что открывает |
|---|---|
| `protected-files` | правку `.claude/`, `.github/workflows/`, `CLAUDE.md` |
| `git-branch` | создание веток вне соглашения |
| `git-push-main` | прямой push в `main`, `master`, `develop` |
| `git-history` | `git reset --hard`, `git clean -f` |
| `git-worktree` | создание и удаление рабочих копий |

Рабочие копии создаются **внутри репозитория**, в `.worktrees/`: путь наружу
отклоняет `guard-scope`, у которого пропусков нет по замыслу — граница «наружу
не писать» не должна открываться ради удобства. Папка в `.gitignore`, сканер
недоверенного текста её пропускает.

Три свойства, без которых это было бы украшением:

- **Пропуск сгорает.** От минуты до двух часов, по умолчанию пятнадцать минут.
  Бессрочное разрешение — это не подтверждение, а снятие запрета.
- **Пропуск нельзя выдать себе.** `scripts/unlock.sh` отказывается работать, если
  видит переменные сессии агента (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`), а сам
  запуск скрипта из сессии заблокирован хуком. Выдаёт сэр, в своём терминале.
- **Использование видно.** Каждое срабатывание по открытой зоне пишется
  в `.claude/logs/guard.jsonl` событием `unlock-used`, выдача — событием `unlock-issued`.

## Что нашло внешнее ревью

Первая версия хуков была отдана на проверку модели другого вендора
(`scripts/review_codex.py`, вердикт целиком — [docs/reviews/2026-08-24-codex-guards.json](reviews/2026-08-24-codex-guards.json)).
Вердикт: **block**, пять находок, из них два блокера. Все подтвердились.

| Находка | Было | Стало |
|---|---|---|
| `guard-scope` обходился относительным путём | `echo x > ../../outside/file` проходило | путь разворачивается в тот, куда команда попадёт |
| `guard-scope` обходился кавычками и `$HOME` | `rm "$HOME/outside"` проходило | `$HOME`, `${HOME}`, `~` и кавычки снимаются до сравнения |
| `guard-scope` смотрел на список опасных команд | `sed -i`, `python3 -c open(...,'w')` проходили | проверяется намерение записи; встроенный код с путём наружу отказывается целиком |
| `guard-secrets` не знал `$HOME/.aws/credentials` | шаблон ждал буквальный `~` | сравнивается развёрнутая строка |
| `sudo` ловился в любом упоминании | `rg sudo README.md` блокировалось | `sudo` должен стоять в позиции команды |

На каждую находку в `scripts/test_hooks.py` добавлен регрессионный тест.
Пятая находка ревьюера — «в репозитории обнаружены инструкции для агента
(`CLAUDE.md`)» — не дефект, а правильное поведение: внешнему ревьюеру велено
считать содержимое репозитория данными и сообщать о встреченных инструкциях.
Он так и сделал.

## Что нашлось в обычной работе, 24–25 августа

Внешнее ревью ищет дыры специально. Эти семь нашлись сами, пока обвязкой
пользовались по назначению, — и это ровно тот сорт находок, ради которого механизм
проверяют работой, а не чтением.

| Находка | В чём была ошибка | Как закрыто |
|---|---|---|
| Гейт качества не видел ни одного прогона тестов | `mark-verify` знал `pytest`, `jest`, `npm test`, но не знал `scripts/test_hooks.py` — единственные тесты, которые тогда были в проекте. Гейт блокировал завершение любой сессии с правкой кода | шаблоны дополнены, три регрессионных теста |
| Зелёный прогон трижды записан красным | детектор искал `failed` без учёта регистра: сработал на печати поля `failed=False`, на заголовке теста со словом `FAILED` и на строке `19:21:30 failed = True`, где «30 failed» прочиталось как счётчик провалов | источник истины — код возврата, текст лишь дополняет маркерами, которые вне отчёта о провале не встречаются |
| `ask` пропускает, а не останавливает | в неинтерактивной сессии диалог не показывается. Правка защищённого хука и создание ветки прошли, оставив в журнале запись `ask` и никакого барьера | `ask` заменён отказом и пропуском с истечением |
| Защита хуков обходилась одной командой | `guard-protected-files` висел только на `Write` и `Edit`; `sed -i` по `.claude/hooks/` проходил мимо всех трёх хуков на Bash — проверено запуском | хук подключён к Bash, проверяет намерение записи и упоминание защищённого пути, включая путь внутри встроенного кода |
| `scan-untrusted` не видел текст, пришедший через `gh` | переход задач на GitHub Issues (PR #5) открыл новый путь внешнего текста — `gh issue view`; это `Bash`, а хук висел только на `Read`, `WebFetch`, `WebSearch` | подключён к `PostToolUse` для `Bash`, но сканирует не весь вывод, а только команды из списка ниже — [issue #6](https://github.com/grimurrash/test-task2/issues/6) |
| `guard-git` пропускал голый push при HEAD на защищённой ветке | правило «в `main` только через PR» держалось на поиске буквального имени ветки в тексте команды; голый `git push` и его формы (`git push origin HEAD`, `--all`, `-u origin @`) ветку не называют — она берётся из HEAD. Коммит ушёл в `origin/main` мимо PR, проверено на живом инциденте и повторено прогоном хука (`rc=0`) | добавлена вторая, независимая проверка — по факту: `git rev-parse --abbrev-ref HEAD` в директории из `cwd` события. Складывается с прежней проверкой по имени, не заменяет её — та по-прежнему одна ловит push не с HEAD (`git push origin рабочая-ветка:main`) — [issue #20](https://github.com/grimurrash/test-task2/issues/20) |
| `guard-scope`/`guard-protected-files` могли принять сам worktree за корень | корень брался из `CLAUDE_PROJECT_DIR`/`os.getcwd()`. Внутри linked worktree относительный путь `../<имя-этого-же-worktree>` разворачивался обратно в тот же каталог (`resolved == root`) — самоссылающаяся форма, а не просто «сосед»; набор тестов не ловил это, потому что всегда запускался из одного места. Найдено сессией роли «контракт» на живой работе, воспроизведено проджект-сессией | общий помощник `_hooklib.repo_root()`: корень — от `git rev-parse --git-common-dir`, один и тот же для основной копии и для всех её worktree. `gate-quality` — смежная находка того же дня: `.git` внутри worktree — файл, не папка, и `os.path.isdir` там молча отключал гейт целиком; ослаблено до `os.path.exists`, а сам корень этого хука сознательно **не** сведён к общему — ему нужен каталог, где реально идёт работа — [issue #24](https://github.com/grimurrash/test-task2/issues/24) |

Первые две находки объединяет одно свойство: механизм молчал не потому, что всё
хорошо, а потому, что смотрел не туда. Гейт, который нечем удовлетворить честно,
и гейт, который врёт о красных тестах, одинаково учат себя обходить.

### Обратная сторона: шесть ложных тревог за ту же сессию

Строгость не бесплатна. Как только запреты стали жёсткими, они начали срабатывать
на безобидном — и каждый раз на авторе, а не на злоумышленнике:

| Ложная тревога | Почему сработала | Как сужено |
|---|---|---|
| Зелёный прогон записан красным (дважды) | шаблон ловил слово `failed` в печати собственного состояния и в заголовке теста | маркеры, не встречающиеся вне отчёта о провале; источник истины — код возврата |
| «30 failed» в отметке времени | `\d+\s+failed` совпал с `19:21:30 failed = True` | форма «поле = значение» исключена |
| Коммит заблокирован из-за текста | запрет ловил любое упоминание скрипта выдачи пропусков | сужен до позиции команды: начало строки или после разделителя |
| Чтение файла пропусков заблокировано | `python3 -c` целиком считался намерением записи | у встроенного кода проверяются признаки записи внутри самого кода |
| Арифметика принята за путь наружу | `//60` — целочисленное деление — выглядит как абсолютный путь `//60` | токен из одних цифр и слэшей не считается путём; `../1` и `./7` по-прежнему считаются |
| `guard-git` отказал команде, описывающей этот же баг | текст heredoc-документа (`cat > file <<'EOF' ... git push origin main ... EOF`) содержал форму настоящего push — регулярка не отличала данные от команды | тело heredoc вырезается перед любой проверкой хука; отдельно — «git push» ловится только в позиции запуска команды (начало строки или после `; & \| \n`), не по любому упоминанию в тексте — issue #20 |

Вывод, который стоит держать рядом с описанием любого механизма: **ложная тревога
обесценивает защиту не меньше пропуска.** Запрет, срабатывающий на безобидном,
приучает искать обходной путь — и находить его уже для настоящих случаев.

## Что остаётся дырой

- Песочница Claude Code накрывает Bash и его дочерние процессы, но **не MCP**.
  Хуки перехватывают вызовы инструментов, но подключённый MCP-сервер со своими
  правами — отдельный разговор.
- `guard-scope` по-прежнему разбирает команду регулярками, а не парсером shell.
  Нормализация закрыла найденные обходы, но перечень способов записать файл
  принципиально не закрывается списком: рекомендация ревьюера — ограничение
  на уровне песочницы или прав файловой системы, и она верна. Хук здесь —
  дополнительный барьер, а не гарантия.
- Широкие шаблоны `guard-secrets` дают ложные срабатывания (любой `.pem`,
  включая публичные сертификаты и тестовые fixtures). Это выбор в пользу
  отказа по умолчанию; клапан — `.claude/guard-allow.txt`.
- Пропуск опирается на переменные окружения (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`),
  чтобы отличить сэра от агента. Переменную можно снять — `env -u CLAUDECODE bash …`.
  Против случайности и против собственной небрежности это работает, против
  целенаправленного обхода — нет; настоящая граница здесь тоже уровня ОС.
- Список защищённых упоминаний в `guard-protected-files` — перечисление. Файл правил,
  названный иначе (символьная ссылка, копия, путь через `$PWD`), в него не попадёт.
- Хуки живут в репозитории и применяются, когда сессия открыта **в этой папке**.
  Смена директории на лету их не подключает — проверено: команда прошла мимо
  запрета, в журнале записи не появилось.
- `scan-untrusted` на `Bash` сканирует не весь вывод, а перечень команд:
  `gh issue view/list/comment`, `gh pr view`, `curl`, `wget`. Осознанный выбор —
  сканировать всё подряд зашумило бы сессию находками на собственных тестах
  репозитория (см. таблицу выше). Обратная сторона: внешний текст, пришедший
  через команду не из списка — `gh api`, `ssh`, кастомный скрипт с HTTP-запросом,
  — хук пропустит молча. Список требует ручного расширения по мере появления
  новых способов затянуть текст снаружи.
- Проверка `guard-git` по HEAD (issue #20) смотрит на `cwd` события хука —
  директорию, где Claude Code запускает команду, — а не разбирает `cd` внутри
  самой строки. `cd .worktrees/psp-x && git push` проверится по HEAD того `cwd`,
  с которого стартовала команда, а не по ветке `.worktrees/psp-x` после `cd`.
  Разбор `cd` в теле команды — это парсер shell, а не точечная правка.
- Та же проверка понимает один heredoc на команду. Несколько heredoc-документов
  подряд или вложенный heredoc она не разбирает — текст в них не вырезается
  и с точки зрения регулярок остаётся текстом, а не командой (то есть в худшем
  случае это пропуск проверки, а не ложный отказ).
- Если `git rev-parse --abbrev-ref HEAD` не смог ответить (не git-репозиторий
  по данному `cwd`, detached HEAD, git отсутствует, истёк 5-секундный таймаут) —
  проверка по HEAD молчит и не блокирует. Дыра не остаётся голой: проверка по
  буквальному имени ветки в тексте команды по-прежнему работает независимо.
- Проверка по имени ветки понимает короткий refspec с двоеточием
  (`origin ветка:main`), но не длинную форму `refs/heads/...:refs/heads/main`.
- Общий корень `_hooklib.repo_root()` (issue #24) сам зависит от git: сбой
  (не репозиторий по данному `cwd`, git недоступен, истёк 5-секундный таймаут)
  откатывает к прежнему поведению — `CLAUDE_PROJECT_DIR`/`os.getcwd()`, то есть
  к тому же классу неточности, что и была. Дыра не расширена, но и не закрыта
  полностью — закрыта ровно в случаях, когда git отвечает.
- Эмпирическая оговорка к issue #24: в живой сессии `CLAUDE_PROJECT_DIR`
  не меняется при `cd` агента в worktree — проверено отладочным прогоном сразу
  на двух параллельных ролях. Найденная дыра воспроизводится надёжно через
  тестовый харнесс (`scripts/test_hooks.py`, запущенный изнутри worktree, сам
  выставляет `CLAUDE_PROJECT_DIR` на своё расположение) и потенциально — если
  сессия когда-либо будет запущена не из основной копии, а прямо из worktree.
  Хуки исправлены на факт вместо допущения в любом случае: полагаться на то,
  что обвязка сегодня ведёт себя определённым образом, — держать границу на
  допущении, а не на гарантии.
- Проверка `gate-quality` по-прежнему смотрит на `data.get("cwd") или
  CLAUDE_PROJECT_DIR`, а не на общий корень — сознательно, ей нужен каталог,
  где реально шла работа. Если `cwd` в Stop-событии окажется недостоверным
  индикатором «где сессия работала последней» — а это не проверено эмпирически
  так же строго, как для PreToolUse, — гейт может проверить не тот working
  tree. Написано как граница, а не как подтверждённый факт.

Это записано здесь, а не умолчано, потому что защита с неизвестными границами
хуже, чем защита с известными.

## Журналы

- `.claude/logs/guard.jsonl` — каждый отказ и каждый запрос подтверждения
- `.claude/logs/untrusted.jsonl` — найденные скрытые инструкции
