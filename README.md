# Идемпотентный платёжный сервис

Учебный проект: приём платежей, устойчивый к повторам. Один и тот же запрос,
отправленный дважды, создаёт один платёж — и это видно, а не декларируется.

Три части, поднимаются одной командой:

| Часть | Что делает | Адрес |
|---|---|---|
| API | приём и отмена платежей, идемпотентность по `Idempotency-Key` | http://localhost:8080 |
| Песочница | нажать и увидеть: повтор возвращает тот же платёж | http://localhost:8081 |
| Документация | описание API из контракта `openapi/openapi.yaml` | http://localhost:8082 |

## Предусловие

**Только Docker.** Ни Node, ни npm, ни базы данных ставить не нужно — всё
собирается и живёт в контейнерах.

Проверить, что он есть:

```bash
docker version
```

## Запуск

```bash
docker compose up
```

Первый запуск собирает три образа — это несколько минут. Дальше секунды.
Когда в выводе появится `backend  Healthy`, открывайте песочницу:
**http://localhost:8081**.

Фоном, без занятого терминала:

```bash
docker compose up -d
docker compose ps
```

## Проверка, что всё живо

```bash
# API отвечает
curl -s -o /dev/null -w '%{http_code}\n' -H 'X-Merchant-Id: demo-shop' \
  http://localhost:8080/v1/payments        # ждём 200

# заявленное поведение целиком: повтор даёт тот же платёж, конфликт ключа — 409,
# отмена идемпотентна, отмена завершённого отклоняется
bash scripts/acceptance.sh
```

Тесты API прогоняются в контейнере, на машине проверяющего ничего для этого
не нужно:

```bash
docker compose run --rm backend-test
```

Сервис `backend-test` — отдельный и намеренно: рабочий образ API собран без
инструментов разработки и исходников тестов, поэтому тесты в нём не запустятся
by design. Обычному `docker compose up` он не мешает — спрятан за профилем.

## Остановка и пересборка

```bash
docker compose down                # остановить и убрать контейнеры
docker compose up --build          # пересобрать образы и поднять
docker compose down --rmi local    # убрать и образы тоже
```

## Если порт занят

Порты меняются переменными окружения, **править файлы не нужно**:

```bash
API_PORT=18080 SANDBOX_PORT=18081 DOCS_PORT=18082 docker compose up --build
```

`--build` здесь обязателен, если меняется `API_PORT`. Причина: адрес API
вшивается в песочницу **на сборке** — статика не читает конфигурацию в момент
запуска. Без пересборки песочница продолжит стучаться на прежний порт, и это
проявится не ошибкой, а молчанием (см. ниже).

## Состояние живёт в памяти

Платежи хранятся в памяти контейнера. **`docker compose restart` или `down`
обнуляют всё** — это ожидаемое поведение песочницы, а не потеря данных:
демонстрационный стенд должен начинать с чистого листа, и внешних хранилищ
проект намеренно не заводит.

## Если не поднялось

**Песочница открывается, но кнопки ничего не делают, платежи не появляются.**
Откройте консоль браузера (F12). Если там ошибка CORS или «Failed to fetch» —
песочница обращается не туда, куда смотрит API. Почти всегда это смена
`API_PORT` без `--build`: пересоберите командой из раздела про порты.
Важно понимать: в браузере отказ по CORS выглядит **точно так же**, как обрыв
сети или выключенный API, — по одному экрану их не различить, поэтому смотреть
нужно именно консоль.

**`port is already allocated`.** Порт занят другим процессом — часто ранее
поднятым контейнером этого же проекта. Посмотреть, кто держит:

```bash
docker ps --format '{{.Names}} {{.Ports}}'
```

Либо остановите его, либо поднимайтесь на других портах (раздел выше).

**`backend` бесконечно в статусе `health: starting`, песочница не стартует.**
Песочница ждёт, пока API станет здоровым, — это намеренно: иначе она поднялась
бы и молчала. Смотрите, что говорит API:

```bash
docker compose logs backend --tail 50
```

**Сборка документации падает.** Она собирается из корня репозитория, потому что
читает `openapi/openapi.yaml` и токены дизайна. Если запускаете `docker build`
руками — контекст должен быть корнем, а не папкой `docs-site/`. Через
`docker compose` это учтено.

**Не собирается вообще ничего, ошибки сети.** Сборка тянет базовые образы
и зависимости из интернета — первый запуск требует сети. Дальше работает
из кеша.

## Как это устроено

```
backend/     API на TypeScript, тесты node:test
frontend/    песочница на React + Vite, статика за nginx
docs-site/   страница документации, собирается из контракта
openapi/     контракт OpenAPI 3.1 — единый источник правды для всех трёх частей
scripts/     приёмочный сценарий, проверки обвязки
docs/        требования, план, описание механизмов
sessions/    журналы ролевых сессий
```

Три части собираются из **разных контекстов**, и это не небрежность:
документация читает контракт во время сборки, песочница прочитала его заранее
(типы закоммичены), API не читает вовсе — контракт монтируется только в тесты.
Подробности — комментарием в `compose.yaml`.

## Про способ работы

Проект сделан **соло, с ролевым разделением по сессиям** — контракт, дизайн,
бэкенд, фронт, документация, обвязка, QA вели отдельные сессии агента,
не видящие контекста друг друга и общающиеся через задачи в трекере и файлы
в репозитории. Это **не команда людей**: разделение обязанностей здесь
инженерный приём, а не организационный факт, и в отчётности называется так же.

## Агентная обвязка

Репозиторий несёт собственные механизмы безопасности: правила здесь живут
в коде, а не в прозе — восемь хуков, гейт качества, поиск скрытых инструкций
во внешнем тексте.

```bash
python3 scripts/test_hooks.py        # проверки хуков
python3 scripts/ci/scan_secrets.py   # секреты в отслеживаемых файлах
python3 scripts/scan_untrusted.py .  # скрытые инструкции в текстах
```

Всё это же гоняется в CI на каждый push и pull request. Подробности —
[docs/HOOKS.md](docs/HOOKS.md), процедура работы — [docs/WORKFLOW.md](docs/WORKFLOW.md).
